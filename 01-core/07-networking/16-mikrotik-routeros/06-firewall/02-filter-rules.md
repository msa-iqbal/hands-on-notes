# Firewall Filter Rules

Firewall filter rules control which packets are accepted, dropped, or rejected by a MikroTik router.

In RouterOS, filter rules are evaluated in order. When a packet matches a rule, the configured action is applied. Rule order is therefore critical: a broad rule placed before a specific rule can prevent the specific rule from ever being evaluated.

Firewall filter rules are configured under:

```routeros
/ip/firewall/filter
```

A filter rule can inspect packet properties such as:

* Source and destination IP addresses
* Source and destination ports
* Incoming and outgoing interfaces
* IP protocols
* Connection states
* Connection NAT states
* TCP flags
* Packet and connection marks

# 🗁 Firewall Filter Chains

RouterOS provides three primary filter chains.

| Chain | Purpose | Example |
| --- | --- | --- |
| `input` | Controls packets destined for the router itself | SSH or WinBox access to the router |
| `forward` | Controls packets passing through the router | LAN clients accessing the internet |
| `output` | Controls packets generated by the router | Router-originated DNS or NTP traffic |

**Input chain**

The `input` chain protects the router's own services and management plane.

Examples include:

* Allowing established connections.
* Allowing management access from a trusted LAN.
* Allowing ICMP traffic to the router.
* Dropping unauthorized access from the WAN.

**Forward chain**

The `forward` chain controls traffic routed between networks.

Examples include:

* Allowing LAN clients to access the internet.
* Blocking traffic from the WAN to internal networks.
* Restricting communication between VLANs.
* Allowing selected port-forwarded connections.

**Output chain**

The `output` chain controls traffic generated by the router itself.

Examples include:

* DNS queries generated by the router.
* NTP synchronization.
* Router-originated monitoring traffic.
* Connections initiated by RouterOS services.

# 🗁 Filter Rule Structure

A typical filter rule contains matching conditions and an action.

```routeros
/ip/firewall/filter
add chain=input src-address=192.168.10.0/24 action=accept
```

Important properties:

| Property | Description |
| --- | --- |
| `chain` | Specifies the filter chain |
| `src-address` | Matches the packet's source IP address |
| `dst-address` | Matches the packet's destination IP address |
| `protocol` | Matches the IP protocol |
| `src-port` | Matches the source port |
| `dst-port` | Matches the destination port |
| `in-interface` | Matches the incoming interface |
| `out-interface` | Matches the outgoing interface |
| `connection-state` | Matches the connection tracking state |
| `connection-nat-state` | Matches the NAT state of a connection |
| `action` | Specifies what happens when the rule matches |
| `comment` | Adds a description to the rule |

A rule can contain multiple matching conditions. All specified conditions must match for the rule to apply.

# 🗁 Common Filter Actions

| Action | Description |
| --- | --- |
| `accept` | Allows the packet |
| `drop` | Silently discards the packet |
| `reject` | Discards the packet and sends a rejection response |
| `fasttrack-connection` | FastTracks eligible established connections |
| `jump` | Sends packet processing to another custom chain |
| `return` | Returns processing from a custom chain |
| `log` | Logs matching packets and continues processing |

The `log` action is not a final filtering decision. A subsequent rule must determine whether the packet is accepted or dropped.

# 🗁 Connection Tracking States

RouterOS connection tracking identifies the state of network connections.

The `connection-state` property allows firewall rules to make decisions based on these states.

| State | Description |
| --- | --- |
| `new` | A packet that starts a new connection |
| `established` | A packet belonging to an established connection |
| `related` | A packet associated with an existing connection |
| `invalid` | A packet that cannot be associated with a valid connection |
| `untracked` | A packet excluded from connection tracking |

Common connection-state matching:

```routeros
/ip/firewall/filter
add chain=input connection-state=established,related action=accept
add chain=input connection-state=invalid action=drop
```

The first rule accepts packets belonging to established or related connections. The second drops packets classified as invalid.

# 🗁 Basic Input Chain Configuration

The following example creates a basic input-chain policy for a router with:

* LAN interface: `bridge-LAN`
* LAN subnet: `192.168.10.0/24`
* WAN interface: `ether1`

First, allow established and related connections.

```routeros
/ip/firewall/filter
add chain=input connection-state=established,related action=accept comment="Allow established and related"
```

Drop invalid packets.

```routeros
/ip/firewall/filter
add chain=input connection-state=invalid action=drop comment="Drop invalid packets"
```

Allow ICMP traffic to the router.

```routeros
/ip/firewall/filter
add chain=input protocol=icmp action=accept comment="Allow ICMP"
```

Allow management access from the trusted LAN.

```routeros
/ip/firewall/filter
add chain=input in-interface=bridge-LAN src-address=192.168.10.0/24 action=accept comment="Allow trusted LAN management"
```

Drop other traffic arriving from the WAN.

```routeros
/ip/firewall/filter
add chain=input in-interface=ether1 action=drop comment="Drop other WAN input"
```

These rules illustrate a basic policy. A production router may require additional rules for VPN access, monitoring, routing protocols, DHCP, DNS, or other services depending on its configuration.

# 🗁 Basic Forward Chain Configuration

The forward chain controls traffic passing through the router.

For a simple LAN-to-internet setup, established and related connections should be allowed first.

```routeros
/ip/firewall/filter
add chain=forward connection-state=established,related action=accept comment="Allow established and related"
```

Drop invalid packets.

```routeros
/ip/firewall/filter
add chain=forward connection-state=invalid action=drop comment="Drop invalid packets"
```

Allow LAN clients to access the internet through the WAN interface.

```routeros
/ip/firewall/filter
add chain=forward in-interface=bridge-LAN out-interface=ether1 action=accept comment="Allow LAN to WAN"
```

Drop other traffic arriving from the WAN.

```routeros
/ip/firewall/filter
add chain=forward in-interface=ether1 action=drop comment="Drop other WAN forwarding"
```

This is a simplified example. Networks using VLANs, multiple WAN interfaces, VPNs, or port forwarding need additional rules that reflect their traffic policies.

# 🗁 Allowing Specific Services

Firewall rules can allow access to specific router services by matching protocol and destination port.

For example, allow SSH access from the trusted LAN:

```routeros
/ip/firewall/filter
add chain=input in-interface=bridge-LAN src-address=192.168.10.0/24 protocol=tcp dst-port=22 action=accept comment="Allow SSH from LAN"
```

Allow WinBox access from the trusted LAN:

```routeros
/ip/firewall/filter
add chain=input in-interface=bridge-LAN src-address=192.168.10.0/24 protocol=tcp dst-port=8291 action=accept comment="Allow WinBox from LAN"
```

Allow DNS requests to the router from the LAN:

```routeros
/ip/firewall/filter
add chain=input in-interface=bridge-LAN src-address=192.168.10.0/24 protocol=udp dst-port=53 action=accept comment="Allow DNS UDP from LAN"
```

If DNS over TCP is required:

```routeros
/ip/firewall/filter
add chain=input in-interface=bridge-LAN src-address=192.168.10.0/24 protocol=tcp dst-port=53 action=accept comment="Allow DNS TCP from LAN"
```

These rules only permit traffic through the firewall. The corresponding RouterOS service must also be enabled and configured to allow the intended clients.

# 🗁 Blocking a Specific IP Address

To block traffic from a specific source address:

```routeros
/ip/firewall/filter
add chain=input src-address=203.0.113.50 action=drop comment="Block unwanted source"
```

To block the same source from forwarding through the router:

```routeros
/ip/firewall/filter
add chain=forward src-address=203.0.113.50 action=drop comment="Block unwanted forwarded source"
```

The `input` and `forward` chains serve different purposes. Blocking an address in one chain does not automatically block it in the other.

# 🗁 Blocking a Specific Port

To block incoming SSH connections from the WAN:

```routeros
/ip/firewall/filter
add chain=input in-interface=ether1 protocol=tcp dst-port=22 action=drop comment="Block WAN SSH access"
```

To block HTTP traffic forwarded through the router:

```routeros
/ip/firewall/filter
add chain=forward protocol=tcp dst-port=80 action=drop comment="Block forwarded HTTP"
```

A port-based rule should be scoped to the intended interfaces, addresses, and traffic direction whenever possible.

# 🗁 Allowing Port-Forwarded Connections

Destination NAT redirects incoming traffic to an internal server. The forward chain must also permit the translated connection.

For example, suppose:

* WAN interface: `ether1`
* Internal server: `192.168.10.100`
* External service: TCP port `443`

A corresponding filter rule can allow destination-NAT connections:

```routeros
/ip/firewall/filter
add chain=forward in-interface=ether1 connection-nat-state=dstnat protocol=tcp dst-address=192.168.10.100 dst-port=443 action=accept comment="Allow forwarded HTTPS"
```

This rule permits matching destination-NAT traffic. The destination NAT rule must also exist, and the server must be reachable through the router.

# 🗁 Rule Ordering and Processing

RouterOS evaluates filter rules sequentially within a chain.

Consider the following example:

```routeros
/ip/firewall/filter
add chain=input action=drop comment="Drop all input"
add chain=input src-address=192.168.10.0/24 action=accept comment="Allow LAN"
```

The LAN rule will not be reached because the first rule already drops every packet entering the input chain.

The correct order is:

```routeros
/ip/firewall/filter
add chain=input src-address=192.168.10.0/24 action=accept comment="Allow LAN"
add chain=input action=drop comment="Drop other input"
```

General ordering principles:

* Place specific allow or deny rules before broader rules when required.
* Handle established and related connections early.
* Drop invalid connections early.
* Place final drop rules after all required allow rules.
* Review existing rules before adding new rules.
* Keep related rules organized and documented.

# 🗁 Managing Filter Rules

List all firewall filter rules:

```routeros
/ip/firewall/filter/print
```

Display rules with their internal details:

```routeros
/ip/firewall/filter/print detail
```

Display rules with packet and byte counters:

```routeros
/ip/firewall/filter/print stats
```

Disable a rule:

```routeros
/ip/firewall/filter/disable [find comment="Block unwanted source"]
```

Enable a rule:

```routeros
/ip/firewall/filter/enable [find comment="Block unwanted source"]
```

Remove a rule:

```routeros
/ip/firewall/filter/remove [find comment="Block unwanted source"]
```

Reset counters:

```routeros
/ip/firewall/filter/reset-counters-all
```

Move a rule to a different position:

```routeros
/ip/firewall/filter/move [find comment="Allow trusted LAN management"] 0
```

Use comments that uniquely identify rules when managing them with `find`.

# 🗁 Logging Firewall Traffic

The `log` property can be enabled on a filter rule to record matching packets.

```routeros
/ip/firewall/filter
add chain=input in-interface=ether1 action=drop log=yes log-prefix="WAN-DROP: " comment="Log and drop WAN input"
```

The rule logs matching packets and then drops them.

View firewall-related log entries:

```routeros
/log/print where message~"WAN-DROP"
```

Logging can help identify unwanted traffic and troubleshoot firewall behavior. Avoid excessive logging on high-traffic rules because it can increase CPU and storage pressure.

# 🗁 Custom Firewall Chains

RouterOS supports custom chains that help organize complex firewall policies.

Create a custom chain:

```routeros
/ip/firewall/filter
add chain=LAN-POLICY action=return comment="LAN policy return"
```

Jump to the custom chain from the forward chain:

```routeros
/ip/firewall/filter
add chain=forward in-interface=bridge-LAN action=jump jump-target=LAN-POLICY comment="Process LAN policy"
```

Add a rule to the custom chain:

```routeros
/ip/firewall/filter
add chain=LAN-POLICY protocol=tcp dst-port=23 action=drop comment="Block Telnet from LAN"
```

Custom chains allow firewall policies to be divided into smaller logical groups. A `return` action sends processing back to the calling chain.

# 🗁 FastTrack Considerations

FastTrack can improve forwarding performance by reducing processing overhead for eligible established connections.

Example:

```routeros
/ip/firewall/filter
add chain=forward connection-state=established,related action=fasttrack-connection hw-offload=yes comment="FastTrack established connections"
```

A common arrangement is to place the FastTrack rule before the regular established/related accept rule.

```routeros
/ip/firewall/filter
add chain=forward connection-state=established,related action=fasttrack-connection hw-offload=yes comment="FastTrack connections"
add chain=forward connection-state=established,related action=accept comment="Allow established and related"
```

FastTrack bypasses parts of the normal packet-processing path. This can affect features such as:

* Simple queues and queue trees.
* Traffic accounting and packet inspection.
* Some firewall processing.
* Policy-based routing and routing marks.
* IPsec and other features requiring normal packet processing.

Do not enable FastTrack blindly on routers that depend on features incompatible with FastTrack. Review the RouterOS packet-flow documentation and test the intended configuration.

# 🗁 Safe Firewall Configuration Practices

* Restrict router management access to trusted networks.
* Avoid exposing WinBox, SSH, or other management services directly to the internet.
* Use explicit interface and source-address matching.
* Allow established and related traffic where appropriate.
* Drop invalid traffic.
* Review rule order after every change.
* Use meaningful comments.
* Avoid unnecessary logging on high-volume traffic.
* Test changes before applying them to production routers.
* Keep a backup and maintain an alternative management path.
* Review IPv4 and IPv6 firewall policies separately.

# 🗁 Troubleshooting Filter Rules

**A service is unreachable**

Check whether the traffic reaches the expected chain and whether an earlier rule drops it.

```routeros
/ip/firewall/filter/print stats
```

**A port-forwarded service does not work**

Verify the destination NAT rule, the forward-chain permission, the server address, and the server's own firewall.

```routeros
/ip/firewall/nat/print
/ip/firewall/filter/print
```

**A LAN client cannot access the internet**

Check the forward chain, routing table, and source NAT configuration.

```routeros
/ip/firewall/filter/print stats
/ip/route/print
/ip/firewall/nat/print
```

**A rule appears not to match**

Check the actual source and destination addresses, interfaces, protocol, ports, connection state, and rule position.

**A rule counter does not increase**

Confirm that the traffic traverses the expected chain and that an earlier rule or FastTrack processing is not affecting the observed traffic.

# 🗁 Practical Lab

**Objective:** Configure basic input and forward filtering for a small LAN.

Network assumptions:

| Component | Configuration |
| --- | --- |
| WAN interface | `ether1` |
| LAN interface | `bridge-LAN` |
| LAN subnet | `192.168.10.0/24` |
| Router LAN address | `192.168.10.1` |

Apply the following rules in the listed order:

```routeros
/ip/firewall/filter
add chain=input connection-state=established,related action=accept comment="Allow established and related input"
add chain=input connection-state=invalid action=drop comment="Drop invalid input"
add chain=input protocol=icmp action=accept comment="Allow ICMP to router"
add chain=input in-interface=bridge-LAN src-address=192.168.10.0/24 action=accept comment="Allow trusted LAN access"
add chain=input action=drop comment="Drop other router input"

add chain=forward connection-state=established,related action=accept comment="Allow established and related forwarding"
add chain=forward connection-state=invalid action=drop comment="Drop invalid forwarding"
add chain=forward in-interface=bridge-LAN out-interface=ether1 action=accept comment="Allow LAN to WAN"
add chain=forward action=drop comment="Drop other forwarding"
```

**Expected results:**

* Trusted LAN clients can access router services.
* ICMP traffic to the router is permitted.
* Established and related connections are accepted.
* Invalid packets are dropped.
* LAN-to-WAN forwarding is permitted.
* Other traffic destined for the router or passing through it is dropped.

This is a controlled lab policy. Before applying it to an existing router, inspect its current configuration and account for required DHCP, DNS, VPN, routing, management, and other services. Apply firewall changes carefully to avoid locking yourself out.
