# Raw, Mangle, and Filter

RouterOS provides several firewall processing facilities for inspecting, modifying, classifying, and controlling network traffic.

Three important firewall components are:

* **Raw:** Processes packets before connection tracking and can bypass connection tracking for selected traffic.
* **Mangle:** Marks packets, connections, and routing decisions for advanced traffic processing.
* **Filter:** Accepts, drops, or rejects packets based on firewall rules.

Each component serves a different purpose. Understanding their processing order and responsibilities helps build efficient firewall policies, policy-based routing, traffic classification, and network security configurations.

The relevant RouterOS menus are:

```routeros
/ip/firewall/raw
/ip/firewall/mangle
/ip/firewall/filter
```

# 🗁 Raw Firewall

The raw firewall processes packets before connection tracking.

Its primary purposes include:

* Dropping unwanted packets early.
* Excluding selected traffic from connection tracking.
* Reducing connection-tracking workload.
* Applying early packet filtering.

Raw rules are useful when traffic should be discarded before RouterOS performs more expensive processing.

**Raw chains**

| Chain | Purpose |
| --- | --- |
| `prerouting` | Processes incoming packets before connection tracking |
| `output` | Processes packets generated by the router before connection tracking |

**Example: Drop traffic from a known unwanted source**

```routeros
/ip/firewall/raw
add chain=prerouting src-address=198.51.100.50 action=drop comment="Drop unwanted source early"
```

This rule drops packets from the specified source before connection tracking.

The address is an example documentation address. Replace it with an appropriate source address for a real deployment.

**Example: Drop invalid-looking traffic early**

```routeros
/ip/firewall/raw
add chain=prerouting src-address=192.0.2.0/24 action=drop comment="Drop unwanted source range"
```

This example blocks a documentation address range. It does not identify all invalid packets; it simply demonstrates early source-based filtering.

# 🗁 Notrack

The raw firewall supports the `notrack` action.

It excludes matching packets from connection tracking.

Example:

```routeros
/ip/firewall/raw
add chain=prerouting src-address=192.168.100.0/24 action=notrack comment="Exclude selected traffic from tracking"
```

The corresponding traffic must be handled with an appropriate stateless policy.

Important considerations:

* Connection-state matching is unavailable for untracked packets.
* NAT depends on connection tracking and does not work normally for untracked traffic.
* Stateful firewall rules cannot be applied to untracked connections in the usual way.
* Both directions of a communication must be considered when designing an untracked flow.

Use `notrack` only when the network design specifically requires it.

# 🗁 Mangle Firewall

Mangle is used to classify and mark packets and connections.

Unlike filter rules, mangle rules do not primarily decide whether traffic is accepted or dropped.

Mangle is commonly used for:

* Connection marking.
* Packet marking.
* Routing marking.
* Policy-based routing.
* Multi-WAN traffic classification.
* QoS and bandwidth management.
* Traffic identification.

Mangle marks are metadata maintained by RouterOS. They are not fields added to the actual IP packet transmitted over the network.

**Mangle chains**

| Chain | Purpose |
| --- | --- |
| `prerouting` | Processes incoming packets before routing decisions |
| `input` | Processes packets destined for the router |
| `forward` | Processes packets routed through the router |
| `output` | Processes packets generated by the router |
| `postrouting` | Processes packets after routing decisions |

# 🗁 Connection Marking

Connection marking assigns a mark to a tracked connection.

It is useful when multiple packets belonging to the same connection need to be identified consistently.

Example:

```routeros
/ip/firewall/mangle
add chain=prerouting src-address=192.168.10.0/24 connection-mark=no-mark action=mark-connection new-connection-mark=lan-connection passthrough=yes comment="Mark LAN connections"
```

Explanation:

* `chain=prerouting` processes incoming packets before the routing decision.
* `src-address=192.168.10.0/24` matches packets from the LAN subnet.
* `connection-mark=no-mark` matches connections that have not already been marked.
* `action=mark-connection` assigns a connection mark.
* `new-connection-mark=lan-connection` defines the mark.
* `passthrough=yes` allows processing to continue to subsequent mangle rules.

The connection mark remains associated with the tracked connection.

# 🗁 Packet Marking

Packet marking assigns a mark to individual packets.

It is commonly used to classify traffic for queue trees and other traffic-management features.

Example:

```routeros
/ip/firewall/mangle
add chain=prerouting src-address=192.168.10.0/24 action=mark-packet new-packet-mark=lan-packets passthrough=no comment="Mark LAN packets"
```

The rule marks matching packets with `lan-packets`.

Packet marks are different from connection marks:

| Connection Mark | Packet Mark |
| --- | --- |
| Associated with a tracked connection | Associated with an individual packet |
| Helps classify complete connections | Helps classify packets for processing |
| Useful for multi-WAN classification | Useful for QoS and queue trees |
| Persists across packets in a connection | Applied to each matching packet |

# 🗁 Routing Marks

Routing marks allow RouterOS to select a routing table for matching packets.

They are commonly used for policy-based routing and multi-WAN configurations.

Example:

```routeros
/ip/firewall/mangle
add chain=prerouting src-address=192.168.20.0/24 action=mark-routing new-routing-mark=to-wan2 passthrough=no comment="Route selected LAN through WAN2"
```

The routing table must exist and contain suitable routes.

Example routing-table configuration:

```routeros
/routing/table
add name=to-wan2 fib
```

Example default route:

```routeros
/ip/route
add dst-address=0.0.0.0/0 gateway=192.0.2.1@main routing-table=to-wan2
```

The gateway address is illustrative. Replace it with the actual next-hop address or appropriate gateway configuration.

A routing mark alone does not create a usable route. The selected routing table must have a valid route to the destination.

Also consider router-originated traffic separately. Traffic generated by the router generally requires appropriate output-chain marking or routing rules.

# 🗁 Filter Firewall

The filter firewall controls whether packets are accepted, dropped, or rejected.

Its main actions include:

| Action | Description |
| --- | --- |
| `accept` | Allows matching traffic |
| `drop` | Silently discards matching traffic |
| `reject` | Discards traffic and sends a rejection response when applicable |
| `jump` | Sends processing to a custom chain |
| `return` | Returns processing from a custom chain |

Filter rules are commonly used to implement:

* Router management access control.
* LAN-to-WAN forwarding policies.
* Port-forwarding permissions.
* Network segmentation.
* Stateful firewall policies.
* Protection against unwanted connections.

Example:

```routeros
/ip/firewall/filter
add chain=input connection-state=established,related action=accept comment="Allow established and related"
add chain=input connection-state=invalid action=drop comment="Drop invalid"
add chain=input in-interface=bridge-LAN action=accept comment="Allow LAN access to router"
add chain=input action=drop comment="Drop other router access"
```

This is an illustrative input-chain policy. It assumes the LAN interface is trusted and should be adapted to the actual management requirements.

# 🗁 Processing Order

Raw, mangle, and filter are not interchangeable. They participate in different stages of packet processing.

A simplified incoming packet path is:

```text
Incoming Packet
      |
      v
Raw Prerouting
      |
      v
Connection Tracking
      |
      v
Mangle Prerouting
      |
      v
Destination NAT
      |
      v
Routing Decision
      |
      +----------------------+
      |                      |
      v                      v
   Input                  Forward
      |                      |
      v                      v
 Mangle Input          Mangle Forward
      |                      |
      v                      v
 Filter Input          Filter Forward
      |                      |
      v                      v
 Local Process         Mangle Postrouting
                             |
                             v
                         Source NAT
                             |
                             v
                         Outgoing
```

This is a simplified illustration of the major processing stages. Additional processing stages exist, and locally generated traffic follows a different path.

Important observations:

* Raw prerouting runs before connection tracking.
* Mangle prerouting runs after connection tracking and before destination NAT.
* Destination NAT occurs before the routing decision.
* Filter input and filter forward evaluate different traffic destinations.
* Mangle postrouting can process packets after the routing decision.
* Source NAT is performed in the outgoing packet-processing path.

# 🗁 Raw vs Mangle vs Filter

| Feature | Raw | Mangle | Filter |
| --- | --- | --- | --- |
| Main purpose | Early packet processing | Traffic classification and marking | Access control |
| Connection tracking | Before tracking | After tracking | Normally after tracking |
| Drop packets | Yes | Not its primary purpose | Yes |
| Accept packets | No general filter-style accept action | Not its primary purpose | Yes |
| Reject packets | No | No | Yes |
| Connection marking | No | Yes | No |
| Packet marking | No | Yes | No |
| Routing marking | No | Yes | No |
| Notrack | Yes | No | No |
| NAT translation | No | No | No |

# 🗁 Rule Order and Passthrough

Rule order matters in raw, mangle, and filter processing.

RouterOS evaluates matching rules in sequence within the applicable chain.

Mangle also supports the `passthrough` property.

| Setting | Behavior |
| --- | --- |
| `passthrough=yes` | Continues processing subsequent rules |
| `passthrough=no` | Stops processing further rules in the current mangle chain |

Example:

```routeros
/ip/firewall/mangle
add chain=prerouting src-address=192.168.10.0/24 action=mark-connection new-connection-mark=lan-connection passthrough=yes
add chain=prerouting connection-mark=lan-connection action=mark-packet new-packet-mark=lan-packets passthrough=no
```

The first rule marks matching connections. The second rule marks packets belonging to those connections.

# 🗁 Practical Lab: Combining Raw, Mangle, and Filter

**Objective:** Build a simple firewall configuration that:

* Drops a selected unwanted source before connection tracking.
* Marks LAN connections.
* Permits established and related forwarding.
* Allows LAN clients to access the internet.
* Drops other forwarded traffic.

Assumed network:

| Component | Configuration |
| --- | --- |
| WAN interface | `ether1` |
| LAN interface | `bridge-LAN` |
| LAN subnet | `192.168.10.0/24` |
| Example blocked source | `198.51.100.50` |

**Configure raw filtering**

```routeros
/ip/firewall/raw
add chain=prerouting src-address=198.51.100.50 action=drop comment="Drop unwanted source before tracking"
```

**Configure connection marking**

```routeros
/ip/firewall/mangle
add chain=prerouting in-interface=bridge-LAN src-address=192.168.10.0/24 connection-mark=no-mark action=mark-connection new-connection-mark=lan-connection passthrough=yes comment="Mark LAN connections"
```

**Configure filter rules**

```routeros
/ip/firewall/filter
add chain=forward connection-state=established,related action=accept comment="Allow established and related"
add chain=forward connection-state=invalid action=drop comment="Drop invalid"
add chain=forward in-interface=bridge-LAN out-interface=ether1 action=accept comment="Allow LAN to WAN"
add chain=forward action=drop comment="Drop other forwarded traffic"
```

This lab demonstrates the roles of the three facilities. It is not a complete router security policy. A separate input-chain policy, NAT configuration, interface validation, and other protections are required for a complete deployment.

# 🗁 Monitoring and Troubleshooting

Display raw rules:

```routeros
/ip/firewall/raw/print stats
```

Display mangle rules:

```routeros
/ip/firewall/mangle/print stats
```

Display filter rules:

```routeros
/ip/firewall/filter/print stats
```

Display connection tracking entries:

```routeros
/ip/firewall/connection/print
```

Inspect a particular rule:

```routeros
/ip/firewall/mangle/print detail
```

When troubleshooting:

* Verify that rules are placed in the correct chain.
* Check whether packet counters increase.
* Confirm that interface and address matchers are correct.
* Review rule order.
* Check whether connection tracking is enabled where required.
* Verify that routing tables contain valid routes when using routing marks.
* Confirm that packet and connection marks are consistent with the intended QoS or routing policy.
* Check whether FastTrack affects the traffic being inspected or marked.

# 🗁 FastTrack Considerations

FastTrack is an optimization for eligible established connections.

It can bypass parts of the normal firewall processing path for fast-tracked packets. This can affect traffic that depends on mangle processing, queues, accounting, or other features that require packets to follow the regular processing path.

Before enabling FastTrack:

* Understand which traffic should be fast-tracked.
* Identify connections requiring packet marking or detailed inspection.
* Check compatibility with queueing and policy-based routing.
* Test the complete configuration under realistic traffic conditions.

Do not assume every packet in a connection will pass through every firewall rule once FastTrack is active.

# 🗁 Best Practices

* Use raw for appropriate early filtering and carefully designed connection-tracking exclusions.
* Use mangle for traffic classification and marking.
* Use filter for packet access control.
* Keep rules specific and avoid unnecessary broad matches.
* Understand the packet-processing order before creating advanced policies.
* Use meaningful connection, packet, and routing mark names.
* Ensure routing marks reference valid routing tables.
* Review FastTrack compatibility with QoS and policy-based routing.
* Monitor rule counters during troubleshooting.
* Document the purpose of every non-obvious rule.
