# Firewall and NAT Interaction

Firewall filtering and Network Address Translation (NAT) are two closely related RouterOS features, but they perform different functions.

* **Firewall filtering** controls whether packets are accepted, dropped, or rejected.
* **NAT** modifies packet source addresses, destination addresses, or transport-layer ports.

RouterOS uses connection tracking to maintain NAT translations and associate packets with their connections.

Understanding how firewall filtering and NAT interact is essential for configuring internet access, port forwarding, network segmentation, and secure routing.

The relevant RouterOS configuration menus are:

```routeros
/ip/firewall/filter
/ip/firewall/nat
/ip/firewall/connection
```

# 🗁 Firewall vs NAT

Although both features operate on network traffic, their responsibilities are different.

| Feature | Firewall Filter | NAT |
| --- | --- | --- |
| Primary purpose | Control packet access | Translate packet addresses or ports |
| Accept packets | Yes | No |
| Drop packets | Yes | No |
| Reject packets | Yes | No |
| Change source IP | No | Yes |
| Change destination IP | No | Yes |
| Change ports | No | Yes |
| Stateful operation | Uses connection tracking | Uses connection tracking |
| Common use | Security and access control | Internet sharing and address translation |

For example, a source NAT rule can translate a private LAN address into a public WAN address. However, that translation does not automatically permit the packet through the firewall filter.

Likewise, accepting a packet in the firewall does not automatically perform NAT.

# 🗁 RouterOS NAT Chains

RouterOS provides different NAT chains depending on the direction and purpose of translation.

| Chain | Purpose |
| --- | --- |
| `srcnat` | Translates source addresses |
| `dstnat` | Translates destination addresses |
| `input` | Translates destination addresses of packets destined for the router |
| `output` | Translates addresses of packets generated by the router |

The `srcnat` and `dstnat` chains are commonly used for normal internet access and port forwarding.

Example source NAT:

```routeros
/ip/firewall/nat
add chain=srcnat out-interface=ether1 action=masquerade
```

Example destination NAT:

```routeros
/ip/firewall/nat
add chain=dstnat in-interface=ether1 protocol=tcp dst-port=443 action=dst-nat to-addresses=192.168.10.100 to-ports=443
```

The NAT chain determines which translation is applied. The filter chain determines whether the resulting traffic is permitted.

# 🗁 Packet Processing and NAT

To understand the interaction between NAT and filtering, it is important to understand the basic packet-processing sequence.

For routed IPv4 traffic, the simplified flow is:

```text
Incoming Packet
      |
      v
Raw Prerouting
      |
      v
Connection Tracking
      |
      v
Mangle Prerouting
      |
      v
Destination NAT
      |
      v
Routing Decision
      |
      +--------------------+
      |                    |
      v                    v
   Input Chain         Forward Chain
      |                    |
      v                    v
   Local Process       Mangle Forward
                           |
                           v
                       Mangle Postrouting
                           |
                           v
                       Source NAT
                           |
                           v
                       Outgoing Interface
```

Locally generated packets follow a different path through output processing.

This diagram is simplified. Actual packet flow includes additional processing stages and can vary according to packet type, connection state, and RouterOS features.

The important points are:

* Destination NAT is performed before the routing decision.
* The routing decision determines whether traffic is destined for the router or must be forwarded.
* The appropriate filter chain evaluates the packet.
* Source NAT is performed later in the outgoing packet-processing path.
* Connection tracking maintains the translation for subsequent packets.

# 🗁 Source NAT and Forward Chain

Source NAT is commonly used when private LAN clients access the internet through a public WAN address.

Assume the following network:

| Component | Configuration |
| --- | --- |
| WAN interface | `ether1` |
| LAN interface | `bridge-LAN` |
| Router WAN IP | `203.0.113.10` |
| Router LAN IP | `192.168.10.1` |
| LAN subnet | `192.168.10.0/24` |
| Client IP | `192.168.10.10` |

A LAN client sends an HTTPS request to an external server.

Before NAT:

```text
Source:      192.168.10.10
Destination: 93.184.216.34
Protocol:    TCP
Destination Port: 443
```

The packet enters the router through `bridge-LAN`.

Because it is being routed toward the internet, the `forward` chain evaluates it.

**Allow LAN-to-WAN forwarding**

```routeros
/ip/firewall/filter
add chain=forward in-interface=bridge-LAN out-interface=ether1 action=accept comment="Allow LAN to WAN"
```

**Apply source NAT**

```routeros
/ip/firewall/nat
add chain=srcnat out-interface=ether1 action=masquerade comment="Masquerade LAN traffic"
```

After NAT:

```text
Source:      203.0.113.10
Destination: 93.184.216.34
Protocol:    TCP
Destination Port: 443
```

The external server sees the translated source address.

When the response returns, connection tracking identifies the connection and reverses the source translation for delivery to the original LAN client.

Important: The source NAT rule does not replace the forward-chain permission. Both routing and firewall filtering must permit the traffic.

# 🗁 Destination NAT and Forward Chain

Destination NAT is commonly used to publish an internal server through a public IP address.

Assume:

| Component | Configuration |
| --- | --- |
| WAN interface | `ether1` |
| Internal server | `192.168.10.100` |
| Public router IP | `203.0.113.10` |
| External service | HTTPS |
| TCP port | `443` |

An external client connects to:

```text
203.0.113.10:443
```

The router translates the destination to:

```text
192.168.10.100:443
```

**Configure destination NAT**

```routeros
/ip/firewall/nat
add chain=dstnat in-interface=ether1 protocol=tcp dst-port=443 action=dst-nat to-addresses=192.168.10.100 to-ports=443 comment="Forward HTTPS to internal server"
```

After destination NAT, the packet is routed toward the internal server.

Because the destination is another network host rather than the router itself, the `forward` chain evaluates it.

**Allow the forwarded connection**

```routeros
/ip/firewall/filter
add chain=forward in-interface=ether1 connection-nat-state=dstnat protocol=tcp dst-address=192.168.10.100 dst-port=443 action=accept comment="Allow forwarded HTTPS"
```

This permits matching destination-NAT traffic.

The server must also be reachable, have the service running, and allow the connection through its own firewall.

# 🗁 Connection NAT State

RouterOS provides the `connection-nat-state` matcher for identifying connections that have undergone NAT.

Common values include:

| Value | Description |
| --- | --- |
| `srcnat` | Connection has source NAT applied |
| `dstnat` | Connection has destination NAT applied |

Example:

```routeros
/ip/firewall/filter
add chain=forward connection-nat-state=dstnat action=accept comment="Allow destination NAT traffic"
```

This rule matches destination-NAT connections.

However, allowing every destination-NAT connection may be broader than intended. A production firewall should normally restrict access by interface, protocol, destination address, and destination port.

# 🗁 NAT Does Not Automatically Permit Traffic

One of the most common firewall configuration mistakes is assuming that creating a NAT rule automatically permits the connection.

Consider this destination NAT configuration:

```routeros
/ip/firewall/nat
add chain=dstnat in-interface=ether1 protocol=tcp dst-port=8080 action=dst-nat to-addresses=192.168.10.100 to-ports=80
```

This rule translates incoming TCP port `8080` traffic to the internal server's TCP port `80`.

It does not automatically permit the translated traffic through the forward filter chain.

A corresponding filter rule is needed when the firewall policy otherwise blocks the connection:

```routeros
/ip/firewall/filter
add chain=forward in-interface=ether1 connection-nat-state=dstnat protocol=tcp dst-address=192.168.10.100 dst-port=80 action=accept comment="Allow forwarded HTTP"
```

Similarly, a source NAT rule does not automatically permit LAN clients to access the internet. The forward chain must allow that traffic.

# 🗁 Input Chain and NAT

The input chain handles packets destined for services running on the router itself.

For example, suppose an external client connects to the router's public IP on TCP port `2222`, and the router redirects that traffic to its own SSH service on TCP port `22`.

A destination NAT rule can translate the destination port:

```routeros
/ip/firewall/nat
add chain=dstnat in-interface=ether1 protocol=tcp dst-port=2222 action=dst-nat to-addresses=203.0.113.10 to-ports=22 comment="Translate external SSH port"
```

If the translated destination is a local router address, the packet is destined for the router and is evaluated by the `input` chain.

A corresponding input rule can permit the translated connection:

```routeros
/ip/firewall/filter
add chain=input in-interface=ether1 connection-nat-state=dstnat protocol=tcp dst-port=22 action=accept comment="Allow translated SSH access"
```

This example illustrates the distinction between traffic forwarded to another host and traffic redirected to a local router service.

Exposing router management services through the internet should be avoided when possible. Prefer a properly secured VPN and restrict management access to trusted sources.

# 🗁 Output Chain and NAT

The output chain handles packets generated by the router itself.

For example, RouterOS may initiate a connection to an external service.

```text
Router
  |
  | Router-generated packet
  |
  v
Output Processing
  |
  v
Internet
```

The NAT `output` chain can modify locally generated packets before routing and subsequent processing.

The NAT `input` chain can modify packets destined for local processing.

These chains are less commonly needed in ordinary home-router and small-office configurations. Use them when a specific router-originated or router-destined translation requirement exists.

# 🗁 NAT and Connection Tracking

RouterOS uses connection tracking to remember NAT translations.

For example, when a client accesses the internet through masquerade, the router records the translation associated with that connection.

This allows response packets to be translated back to the original internal address.

Display tracked connections:

```routeros
/ip/firewall/connection/print
```

Display detailed connection information:

```routeros
/ip/firewall/connection/print detail
```

Display connections with source NAT:

```routeros
/ip/firewall/connection/print where connection-mark=""
```

The last command is not a reliable NAT-state filter. Use connection details and the appropriate firewall matchers to inspect NAT behavior.

# 🗁 NAT Rule Order and Firewall Rule Order

Both NAT and filter rules are evaluated in order, but their processing responsibilities are different.

**NAT rule order**

NAT rules are evaluated within their respective chains. The first matching NAT rule generally establishes the translation for a new connection.

Example:

```routeros
/ip/firewall/nat
add chain=srcnat src-address=192.168.10.0/24 out-interface=ether1 action=src-nat to-addresses=203.0.113.10 comment="Specific LAN source NAT"
add chain=srcnat out-interface=ether1 action=masquerade comment="General WAN masquerade"
```

The specific source NAT rule appears before the general masquerade rule.

**Filter rule order**

Filter rules are evaluated sequentially within each filter chain.

Example:

```routeros
/ip/firewall/filter
add chain=forward connection-state=established,related action=accept comment="Allow established and related"
add chain=forward connection-state=invalid action=drop comment="Drop invalid"
add chain=forward in-interface=bridge-LAN out-interface=ether1 action=accept comment="Allow LAN to WAN"
add chain=forward action=drop comment="Drop other forwarding"
```

Place required permissions before broad drop rules.

# 🗁 Existing Connections and NAT Changes

NAT translations are maintained in connection tracking.

This means changes to NAT rules do not necessarily affect connections that already have an established translation.

For example:

* A client establishes an internet connection.
* RouterOS creates a connection-tracking entry.
* A NAT rule is modified.
* The existing connection may continue using its original translation.

When testing NAT changes, use a new connection or remove the specific existing connection entry when appropriate.

Inspect connections:

```routeros
/ip/firewall/connection/print
```

Remove a selected connection:

```routeros
/ip/firewall/connection/remove numbers=0
```

The number is an example. Inspect the table and select the correct entry before removing it.

Avoid clearing the entire connection table on a production router unless necessary.

# 🗁 Hairpin NAT and Firewall Filtering

Hairpin NAT allows internal clients to access an internal server using the same public IP address that external clients use.

Example network:

| Component | Address |
| --- | --- |
| Router LAN IP | `192.168.10.1` |
| Internal server | `192.168.10.100` |
| Public IP | `203.0.113.10` |
| Internal client | `192.168.10.20` |

The internal client accesses:

```text
203.0.113.10:443
```

Destination NAT redirects the connection to:

```text
192.168.10.100:443
```

A hairpin source NAT rule may also be required so the server returns traffic through the router and the translation can be reversed correctly.

Example destination NAT:

```routeros
/ip/firewall/nat
add chain=dstnat dst-address=203.0.113.10 protocol=tcp dst-port=443 action=dst-nat to-addresses=192.168.10.100 to-ports=443 comment="Hairpin destination NAT"
```

Example hairpin source NAT:

```routeros
/ip/firewall/nat
add chain=srcnat src-address=192.168.10.0/24 dst-address=192.168.10.100 protocol=tcp dst-port=443 out-interface=bridge-LAN action=masquerade comment="Hairpin source NAT"
```

The corresponding forward-chain policy must permit the translated traffic.

Hairpin NAT is useful when internal and external clients need to use the same public service address. Its exact configuration depends on the network's addressing and routing design.

# 🗁 Troubleshooting Firewall and NAT Interaction

**LAN clients cannot access the internet**

Check the forward-chain rules:

```routeros
/ip/firewall/filter/print
```

Check source NAT:

```routeros
/ip/firewall/nat/print
```

Check routing:

```routeros
/ip/route/print
```

Confirm that the LAN client has a valid IP address, gateway, and DNS configuration.

**Port forwarding does not work**

Check the destination NAT rule:

```routeros
/ip/firewall/nat/print
```

Check the forward-chain policy:

```routeros
/ip/firewall/filter/print
```

Also verify that the internal server is reachable and that its service is listening on the expected port.

**NAT rule counters do not increase**

Check:

* Whether the packet reaches the router.
* Whether the correct NAT chain is used.
* Whether the interface and address conditions match.
* Whether the rule is positioned correctly.
* Whether an existing connection is using an earlier translation.

**Port forwarding works from the internet but not from the LAN**

This may indicate a missing hairpin NAT configuration or an alternative internal DNS solution.

**A NAT rule works but traffic is still blocked**

Inspect the relevant filter chain. NAT translation and filter permission are separate operations.

# 🗁 Practical Lab

**Objective:** Configure LAN internet access and publish an internal HTTPS server.

Network assumptions:

| Component | Configuration |
| --- | --- |
| WAN interface | `ether1` |
| LAN interface | `bridge-LAN` |
| Router LAN IP | `192.168.10.1` |
| LAN subnet | `192.168.10.0/24` |
| Internal server | `192.168.10.100` |
| Public router IP | `203.0.113.10` |
| HTTPS port | `443` |

**Allow LAN-to-WAN forwarding**

```routeros
/ip/firewall/filter
add chain=forward connection-state=established,related action=accept comment="Allow established and related"
add chain=forward connection-state=invalid action=drop comment="Drop invalid forwarding"
add chain=forward in-interface=bridge-LAN out-interface=ether1 action=accept comment="Allow LAN to WAN"
```

**Configure source NAT**

```routeros
/ip/firewall/nat
add chain=srcnat src-address=192.168.10.0/24 out-interface=ether1 action=masquerade comment="LAN internet masquerade"
```

**Configure destination NAT**

```routeros
/ip/firewall/nat
add chain=dstnat in-interface=ether1 protocol=tcp dst-port=443 action=dst-nat to-addresses=192.168.10.100 to-ports=443 comment="Forward HTTPS to server"
```

**Allow destination-NAT traffic**

```routeros
/ip/firewall/filter
add chain=forward in-interface=ether1 connection-nat-state=dstnat protocol=tcp dst-address=192.168.10.100 dst-port=443 action=accept comment="Allow forwarded HTTPS"
```

**Verify NAT and filter rules**

```routeros
/ip/firewall/nat/print stats
/ip/firewall/filter/print stats
/ip/firewall/connection/print
```

Test the following:

* LAN client accesses an external website.
* External client accesses the public HTTPS address.
* Internal server receives the forwarded connection.
* NAT and filter counters increase as expected.

This lab assumes the router has a working WAN connection, the internal server is configured correctly, and the public IP is reachable. Existing firewall rules and rule order must be reviewed before applying the examples.

# 🗁 Best Practices

* Treat firewall filtering and NAT as separate functions.
* Understand the packet path before creating rules.
* Use the correct filter chain for the packet's destination.
* Allow only the required forwarded services.
* Restrict port forwarding to specific destinations and ports.
* Avoid exposing router management services directly to the internet.
* Use connection tracking when building stateful firewall policies.
* Keep specific NAT rules before broader matching rules.
* Review existing connections when troubleshooting NAT changes.
* Monitor NAT and filter counters.
* Test changes in a controlled environment before deploying them.
