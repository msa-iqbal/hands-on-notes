# Mangle and Policy Routing

MikroTik RouterOS provides the **Mangle** facility to classify and mark packets and connections as they pass through the router.

Mangle is commonly used for advanced policy routing, multi-WAN load balancing, traffic classification, QoS, and bandwidth management.

In policy routing, Mangle can mark traffic and associate that traffic with a specific routing table.

For example:

* Traffic from LAN-A should use WAN1.
* Traffic from LAN-B should use WAN2.
* Selected connections should use a particular WAN.
* Specific traffic should follow a dedicated routing path.

Unlike basic routing rules, Mangle provides connection marking and packet marking, allowing more flexible traffic classification.

# 🗁 What Is Mangle?

Mangle is a RouterOS firewall facility used to modify packet and connection metadata.

It does not normally modify the actual application data carried inside packets.

Common Mangle actions include:

| Action | Purpose |
| --- | --- |
| `mark-connection` | Assigns a connection mark |
| `mark-packet` | Assigns a packet mark |
| `mark-routing` | Assigns a routing mark |
| `change-dscp` | Changes the DSCP value |
| `change-ttl` | Changes the TTL value |
| `change-mss` | Changes the TCP MSS value |
| `accept` | Stops further Mangle rule processing for the matching packet |
| `passthrough` | Continues processing subsequent rules |

Mangle rules are organized into chains, similar to other RouterOS firewall facilities.

# 🗁 Mangle Chains

The main Mangle chains are:

| Chain | Purpose |
| --- | --- |
| `prerouting` | Processes packets arriving before the routing decision |
| `input` | Processes packets destined for the router |
| `forward` | Processes packets routed through the router |
| `output` | Processes packets generated by the router |
| `postrouting` | Processes packets after the routing decision, before transmission |

For policy routing, the most important chains are:

**prerouting**

Used for marking incoming traffic from LAN clients before the router performs its routing lookup.

**output**

Used for marking traffic generated by the router itself, such as traffic from router-originated services or connections.

**Important:** A routing mark must be applied before the relevant routing lookup. For forwarded traffic, `prerouting` is commonly used. For router-originated traffic, `output` is commonly used.

# 🗁 Understanding Connection Marks

A connection mark identifies a tracked connection.

It is useful when you want to classify an entire connection and apply consistent treatment to its packets.

Example:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.10.0/24 \
    connection-state=new \
    connection-mark=no-mark \
    action=mark-connection \
    new-connection-mark=LAN_A_CONN \
    passthrough=yes \
    comment="Mark LAN-A connections"
```

This rule marks new, unmarked connections originating from `192.168.10.0/24`.

Once a connection is marked, subsequent packets belonging to that tracked connection can match the same connection mark.

Inspect Mangle rules:

```routeros
/ip/firewall/mangle/print
```

Inspect connection tracking entries:

```routeros
/ip/firewall/connection/print
```

Connection marks are especially useful for multi-WAN load balancing and maintaining consistent connection paths.

# 🗁 Understanding Packet Marks

A packet mark identifies individual packets.

Unlike a connection mark, a packet mark is not automatically shared by every packet in a connection.

Example:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.20.0/24 \
    action=mark-packet \
    new-packet-mark=LAN_B_PACKETS \
    passthrough=yes \
    comment="Mark LAN-B packets"
```

Packet marks are commonly used for:

* Queue trees.
* Traffic classification.
* Bandwidth management.
* QoS policies.
* Identifying specific traffic classes.

A packet mark does not automatically select a routing table. Routing selection requires an appropriate routing mechanism, such as `mark-routing`.

# 🗁 Understanding Routing Marks

A routing mark identifies the routing table that should be used for a packet's routing lookup.

In RouterOS v7, routing marks correspond to routing tables.

For example:

```routeros
/routing/table/add name=to_WAN1 fib
```

Then apply a routing mark:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.10.0/24 \
    action=mark-routing \
    new-routing-mark=to_WAN1 \
    passthrough=no \
    comment="Route LAN-A through WAN1"
```

The `new-routing-mark` value must refer to an existing routing table.

The selected table must also contain a suitable route to the destination.

# 🗁 Connection Mark vs. Packet Mark vs. Routing Mark

These marks serve different purposes.

| Mark Type | Scope | Common Use |
| --- | --- | --- |
| Connection mark | Tracked connection | Connection classification and WAN consistency |
| Packet mark | Individual packet | QoS and traffic classification |
| Routing mark | Individual packet | Selecting a routing table |

A typical policy-routing workflow is:

```text
Incoming Packet
      |
      v
Mangle Classification
      |
      v
Connection Mark
      |
      v
Routing Mark
      |
      v
Routing Table Lookup
      |
      v
Selected Gateway
```

This is a simplified representation of a common policy-routing design.

# 🗁 Creating Routing Tables

Before applying routing marks, create the required routing tables.

Example:

```routeros
/routing/table/add name=to_WAN1 fib
/routing/table/add name=to_WAN2 fib
```

Verify the tables:

```routeros
/routing/table/print
```

Custom forwarding tables need the `fib` property.

# 🗁 Adding Routes to Custom Tables

Each routing table needs suitable routes.

Assume:

| WAN | Interface | Gateway |
| --- | --- | --- |
| WAN1 | ether1 | `192.168.1.1` |
| WAN2 | ether2 | `192.168.2.1` |

Add a default route to WAN1's table:

```routeros
/ip/route/add \
    dst-address=0.0.0.0/0 \
    gateway=192.168.1.1 \
    routing-table=to_WAN1 \
    distance=1 \
    comment="WAN1 policy route"
```

Add a default route to WAN2's table:

```routeros
/ip/route/add \
    dst-address=0.0.0.0/0 \
    gateway=192.168.2.1 \
    routing-table=to_WAN2 \
    distance=1 \
    comment="WAN2 policy route"
```

The gateways must be resolvable. If required, configure gateway resolution through the main routing table, for example by using a gateway reference such as `192.168.1.1@main`.

# 🗁 Policy Routing by Source Address

One of the simplest Mangle-based policy-routing configurations is routing traffic according to its source subnet.

Assume:

| Network | Purpose | Routing Table |
| --- | --- | --- |
| `192.168.10.0/24` | LAN-A | `to_WAN1` |
| `192.168.20.0/24` | LAN-B | `to_WAN2` |

First, create an address list containing internal networks that should not be sent through the WAN policy tables.

```routeros
/ip/firewall/address-list/add \
    list=LOCAL_NETWORKS \
    address=192.168.10.0/24

/ip/firewall/address-list/add \
    list=LOCAL_NETWORKS \
    address=192.168.20.0/24
```

Add other internal, management, VPN, and remote networks as appropriate for the actual topology.

Mark LAN-A traffic:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.10.0/24 \
    dst-address-list=!LOCAL_NETWORKS \
    dst-address-type=!local \
    action=mark-routing \
    new-routing-mark=to_WAN1 \
    passthrough=no \
    comment="LAN-A through WAN1"
```

Mark LAN-B traffic:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.20.0/24 \
    dst-address-list=!LOCAL_NETWORKS \
    dst-address-type=!local \
    action=mark-routing \
    new-routing-mark=to_WAN2 \
    passthrough=no \
    comment="LAN-B through WAN2"
```

These rules:

* Match traffic from the specified LAN subnet.
* Exclude destinations listed as internal networks.
* Exclude addresses belonging to the router itself.
* Assign the appropriate routing mark.
* Stop further Mangle rule processing for matching packets.

The address list must represent the internal networks that should retain their normal routing behavior.

# 🗁 Policy Routing with Connection Marks

Connection marks are useful when the routing policy needs to classify connections first and apply routing marks to their packets.

For example, you can classify connections originating from LAN-A and LAN-B.

Mark LAN-A connections:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.10.0/24 \
    dst-address-list=!LOCAL_NETWORKS \
    dst-address-type=!local \
    connection-state=new \
    connection-mark=no-mark \
    action=mark-connection \
    new-connection-mark=LAN_A_CONN \
    passthrough=yes \
    comment="Mark LAN-A connections"
```

Mark LAN-B connections:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    src-address=192.168.20.0/24 \
    dst-address-list=!LOCAL_NETWORKS \
    dst-address-type=!local \
    connection-state=new \
    connection-mark=no-mark \
    action=mark-connection \
    new-connection-mark=LAN_B_CONN \
    passthrough=yes \
    comment="Mark LAN-B connections"
```

Apply the routing mark to LAN-A connections:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    connection-mark=LAN_A_CONN \
    dst-address-list=!LOCAL_NETWORKS \
    dst-address-type=!local \
    action=mark-routing \
    new-routing-mark=to_WAN1 \
    passthrough=no \
    comment="Route LAN-A connections through WAN1"
```

Apply the routing mark to LAN-B connections:

```routeros
/ip/firewall/mangle/add \
    chain=prerouting \
    connection-mark=LAN_B_CONN \
    dst-address-list=!LOCAL_NETWORKS \
    dst-address-type=!local \
    action=mark-routing \
    new-routing-mark=to_WAN2 \
    passthrough=no \
    comment="Route LAN-B connections through WAN2"
```

This separates connection classification from routing-table selection.

It also provides a foundation for more advanced multi-WAN designs.

# 🗁 Handling Router-Originated Traffic

Traffic generated by the MikroTik router itself does not pass through the `prerouting` chain.

Examples include:

* DNS queries generated by the router.
* NTP requests.
* Router-originated ping traffic.
* Connections initiated by router services.
* Monitoring and update traffic.

To apply policy routing to router-originated traffic, use the `output` chain.

Example:

```routeros
/ip/firewall/mangle/add \
    chain=output \
    dst-address-type=!local \
    action=mark-routing \
    new-routing-mark=to_WAN1 \
    passthrough=no \
    comment="Router-originated traffic through WAN1"
```

This example directs matching router-originated traffic through the WAN1 routing table.

For more advanced configurations, classify router-originated connections before applying routing marks. Ensure that router services requiring a different WAN or routing table are handled separately.

# 🗁 Mangle Rule Order

Mangle rules are evaluated in order within their respective chains.

The order matters because an earlier rule can mark traffic, accept it, or stop further processing.

A common policy-routing rule arrangement is:

```text
Mangle prerouting
      |
      v
Exclude internal destinations
      |
      v
Classify new connections
      |
      v
Apply connection marks
      |
      v
Apply routing marks
      |
      v
Continue to routing lookup
```

Use:

* `passthrough=yes` when subsequent Mangle rules should process the packet.
* `passthrough=no` when no further Mangle processing is required for that packet.

Inspect rule order:

```routeros
/ip/firewall/mangle/print
```

Move a rule when necessary:

```routeros
/ip/firewall/mangle/move [find where comment="LAN-A through WAN1"] 0
```

Use the correct position for your actual configuration. Do not move rules blindly on a production router.

# 🗁 Mangle and Routing Rules Interaction

RouterOS supports both Mangle-based policy routing and routing rules.

They can coexist, but overlapping policies need careful design.

A routing mark applied through Mangle can influence routing lookup before ordinary routing-rule processing.

This means an unintended routing mark may cause traffic to use a different table than expected.

For example:

* A Mangle rule marks traffic for `to_WAN1`.
* A routing rule attempts to direct the same traffic to `to_WAN2`.
* The Mangle-based routing policy can take precedence for that marked packet.

When troubleshooting, inspect both configurations:

```routeros
/ip/firewall/mangle/print detail
/routing/rule/print detail
/routing/table/print
```

Avoid creating conflicting policies for the same traffic unless the interaction is intentional.

# 🗁 NAT and Connection Tracking

Mangle-based policy routing must be designed together with NAT and connection tracking.

For a multi-WAN setup, each WAN commonly needs an appropriate source NAT rule.

Example:

```routeros
/ip/firewall/nat/add \
    chain=srcnat \
    out-interface=ether1 \
    action=masquerade \
    comment="NAT through WAN1"

/ip/firewall/nat/add \
    chain=srcnat \
    out-interface=ether2 \
    action=masquerade \
    comment="NAT through WAN2"
```

Connection tracking maintains information about established connections, including their NAT state.

When a connection is assigned to a WAN, its return traffic must be handled consistently.

If traffic leaves through WAN1 but replies arrive through WAN2, asymmetric routing or upstream filtering can interrupt the connection.

For advanced multi-WAN configurations, connection marking is commonly used to preserve connection-path decisions.

# 🗁 FastTrack Considerations

FastTrack can interfere with configurations that depend on Mangle processing.

FastTracked packets can bypass parts of the normal firewall processing path, including Mangle processing.

If a policy-routing design depends on packet or connection marks, make sure the relevant traffic is not incorrectly FastTracked.

For example, a general FastTrack rule may need to exclude policy-routed connections.

A conceptual example:

```routeros
/ip/firewall/filter/add \
    chain=forward \
    action=fasttrack-connection \
    connection-state=established,related \
    connection-mark=no-mark \
    comment="FastTrack unmarked connections"
```

This example FastTracks only connections without a connection mark. It must be integrated into the actual firewall rule order and security policy.

Do not assume that adding a connection mark automatically makes every existing FastTrack configuration safe.

# 🗁 Troubleshooting Mangle Policy Routing

Inspect Mangle rules:

```routeros
/ip/firewall/mangle/print detail
```

Inspect routing rules:

```routeros
/routing/rule/print detail
```

Inspect routing tables:

```routeros
/routing/table/print
```

Inspect routes:

```routeros
/ip/route/print detail
```

Inspect connection tracking:

```routeros
/ip/firewall/connection/print
```

Inspect NAT:

```routeros
/ip/firewall/nat/print
```

Common problems include:

**Traffic uses the wrong WAN**

Possible causes:

* Incorrect source or destination matching.
* An earlier Mangle rule applies a different mark.
* The wrong routing table is selected.
* A routing table contains an incorrect default route.
* Existing connection-tracking entries retain an earlier connection classification.

**Traffic cannot reach internal networks**

Possible causes:

* Internal destinations were not excluded from policy routing.
* The selected routing table does not contain the necessary internal routes.
* A routing mark is applied to traffic that should use the main table.

**Internet access fails after applying routing marks**

Possible causes:

* The custom routing table has no valid default route.
* The gateway cannot be resolved.
* Source NAT is missing.
* Return traffic follows an inconsistent path.
* Firewall rules block the traffic.

**Router-originated traffic uses the wrong WAN**

Possible causes:

* The `output` chain has no appropriate policy.
* A router-originated connection is not classified correctly.
* The selected routing table contains an unexpected route.

# 🗁 Practical Lab: Policy Routing with Two WANs

**Objective:** Route two LAN subnets through different WAN connections using Mangle routing marks.

**Network topology:**

```text

                    |    MikroTik   |
                    +---------------+
                       |         |
                     WAN1      WAN2
                       |         |
                 192.168.1.1 192.168.2.1
                       |
                +------+------+
                |             |
              LAN-A         LAN-B
          192.168.10.0  192.168.20.0
                |             |
              WAN1          WAN2
```

Assume:

* `ether1` connects to WAN1.
* `ether2` connects to WAN2.
* Both WAN gateways are reachable.
* LAN-A uses `192.168.10.0/24`.

# 🗁 Best Practices

* Use descriptive names for connection marks, packet marks, and routing tables.
* Create custom routing tables before referencing them in Mangle rules.
* Exclude internal destinations from WAN policy routing where appropriate.
* Apply routing marks before the routing lookup.
* Use connection marks when consistent connection classification is required.
* Keep Mangle rules organized and document their purpose.
* Review FastTrack rules when using policy routing.
* Configure NAT for each WAN connection.
* Consider return-path consistency in multi-WAN environments.
* Test policy routing with new connections after changing classification rules.
* Avoid applying overlapping routing marks and routing rules without understanding their interaction.

# 🗁 Summary

Mangle provides advanced traffic classification and marking capabilities in RouterOS.

Key points:

* Connection marks classify tracked connections.
* Packet marks identify individual packets.
* Routing marks select routing tables for packet forwarding.
* `prerouting` is commonly used for forwarded traffic.
* `output` is commonly used for router-originated traffic.
* Custom routing tables need suitable routes and the `fib` property.
* NAT and connection tracking are important in multi-WAN policy routing.
* FastTrack must be considered when firewall processing and packet marks are involved.

Mangle-based policy routing is a foundation for advanced multi-WAN configurations, PCC load balancing, and traffic engineering.
