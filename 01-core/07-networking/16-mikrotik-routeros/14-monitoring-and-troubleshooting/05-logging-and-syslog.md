# Logging and Syslog

Logging is an essential monitoring and troubleshooting feature in MikroTik RouterOS. It records system events, network activities, errors, warnings, authentication attempts, and other operational information.

Syslog extends local logging by allowing RouterOS to forward log messages to a centralized logging server.

Together, logging and Syslog help administrators investigate network problems, monitor security events, maintain operational records, and analyze router behavior over time.

# 🗁 Understanding RouterOS Logging

RouterOS logging records events generated by different system components.

Common logging topics include:

| Topic | Description |
| --- | --- |
| `system` | General system events |
| `error` | Error messages |
| `warning` | Warning messages |
| `info` | Informational messages |
| `critical` | Critical system events |
| `firewall` | Firewall-related events |
| `account` | User account activity |
| `interface` | Interface-related events |
| `wireless` | Wireless-related events |
| `dhcp` | DHCP-related events |
| `ppp` | PPP and PPPoE-related events |
| `route` | Routing-related events |
| `script` | Script execution messages |

Available topics depend on the RouterOS version, installed packages, and enabled services.

A log message generally contains:

* Timestamp.
* Logging topics.
* Event description.

# 🗁 Viewing System Logs

Display all available log entries:

```routeros
/log/print
```

The output may contain messages such as:

```text
time=08:15:10 topics=system,info message=router started
time=08:16:20 topics=interface,info message=ether1 link up
time=08:17:05 topics=dhcp,info message=assigned address
```

The output format and message details depend on the event.

# 🗁 Filtering Log Messages

Filtering helps locate specific events without reviewing the entire log.

Display system-related messages:

```routeros
/log/print where topics~"system"
```

Display error messages:

```routeros
/log/print where topics~"error"
```

Display firewall-related messages:

```routeros
/log/print where topics~"firewall"
```

Display DHCP-related messages:

```routeros
/log/print where topics~"dhcp"
```

Display PPP-related messages:

```routeros
/log/print where topics~"ppp"
```

You can combine conditions:

```routeros
/log/print where topics~"firewall" and message~"drop"
```

This searches for log entries whose topics include `firewall` and whose message contains `drop`.

# 🗁 Understanding Logging Actions

RouterOS uses logging actions to determine where log messages are stored or forwarded.

Display configured logging actions:

```routeros
/system/logging/action/print
```

Common logging action types include:

| Action | Purpose |
| --- | --- |
| `memory` | Stores logs in router memory |
| `disk` | Stores logs on local storage |
| `echo` | Displays messages in the terminal |
| `remote` | Sends logs to a remote Syslog server |

Each action has different storage and delivery characteristics.

**Memory logging**

Memory logging stores messages in RAM.

Advantages:

* Easy to access.
* No continuous disk writes.
* Useful for real-time troubleshooting.

Limitations:

* Limited storage capacity.
* Older messages are overwritten when the buffer fills.
* Logs are lost after a reboot.

**Disk logging**

Disk logging stores messages on local storage.

Advantages:

* Logs can survive a reboot.
* Useful for retaining local records.

Limitations:

* Limited storage capacity.
* Frequent writes can increase flash-storage wear.
* Requires storage management.

**Remote logging**

Remote logging forwards messages to another system.

Advantages:

* Centralized log collection.
* Better long-term retention.
* Easier investigation across multiple routers.
* Logs can remain available even if a router restarts.

# 🗁 Configuring Logging Rules

Logging rules determine which topics are recorded and which action handles them.

Display current logging rules:

```routeros
/system/logging/print
```

A basic rule can be configured to record system information in memory:

```routeros
/system/logging/add topics=system,info action=memory
```

Record firewall events:

```routeros
/system/logging/add topics=firewall action=memory
```

Record critical messages:

```routeros
/system/logging/add topics=critical action=memory
```

The logging action determines where the matching messages are sent.

Avoid creating overlapping rules unnecessarily, as the same event may be recorded through multiple matching rules.

# 🗁 Configuring Disk Logging

To configure a disk logging action:

```routeros
/system/logging/action/add name=disk-log target=disk disk-file-name=router-log
```

Create a logging rule:

```routeros
/system/logging/add topics=system,warning action=disk-log
```

Inspect logging actions:

```routeros
/system/logging/action/print
```

Disk logging options vary by RouterOS version and hardware capabilities.

For production systems, configure suitable file sizes and rotation settings where supported. Monitor available storage to prevent logs from consuming excessive disk space.

# 🗁 Understanding Syslog

Syslog is a standard mechanism for transmitting log messages from network devices to centralized logging systems.

A typical Syslog architecture contains:

* Syslog client: MikroTik router that generates log messages.
* Syslog server: System that receives and stores log messages.
* Log storage: Database or files used to retain records.
* Log viewer: Application used to search and analyze events.

Example architecture:

```text
                 Network Devices
                        |
          +-------------+-------------+
          |             |             |
       Router A      Router B      Router C
          |             |             |
          +-------------+-------------+
                        |
                  Syslog Server
                        |
                Centralized Storage
                        |
                  Log Dashboard
```

Centralized logging makes it easier to investigate events across multiple network devices.

# 🗁 Configuring a Remote Syslog Action

Assume the following network configuration:

| Component | Address |
| --- | --- |
| MikroTik router | `192.168.10.1` |
| Syslog server | `192.168.10.100` |
| Syslog transport | UDP |
| Syslog port | `514` |

Create a remote logging action:

```routeros
/system/logging/action/add name=remote-syslog target=remote remote=192.168.10.100 remote-port=514
```

Add a rule to forward system messages:

```routeros
/system/logging/add topics=system,info action=remote-syslog
```

Forward warning and error messages:

```routeros
/system/logging/add topics=warning,error action=remote-syslog
```

Forward firewall-related messages:

```routeros
/system/logging/add topics=firewall action=remote-syslog
```

Verify the configuration:

```routeros
/system/logging/action/print
```

```routeros
/system/logging/print
```

The Syslog server must be configured to listen on the selected address, transport protocol, and port.

# 🗁 Understanding Syslog Transport

Syslog can use different transport protocols.

| Transport | Description |
| --- | --- |
| UDP | Connectionless transport with no delivery guarantee |
| TCP | Connection-oriented transport |
| TLS | Provides encrypted Syslog transport when supported by the implementation |

Traditional Syslog commonly uses UDP port `514`.

UDP does not guarantee delivery, ordering, or retransmission. During network interruptions, log messages may be lost.

TCP provides reliable transport between connected endpoints but does not automatically guarantee permanent storage or application-level processing.

Encrypted Syslog over TLS helps protect log messages during transmission.

RouterOS remote logging capabilities depend on the installed version and supported action properties. Inspect the available options before configuring a particular transport.

# 🗁 Configuring a Syslog Server on Ubuntu

Ubuntu can receive Syslog messages using `rsyslog`.

Install the package:

```bash
sudo apt update
sudo apt install rsyslog
```

Check the service:

```bash
sudo systemctl status rsyslog
```

Create a configuration file:

```bash
sudo nano /etc/rsyslog.d/10-mikrotik.conf
```

Configure UDP reception:

```text
module(load="imudp")
input(type="imudp" port="514")
```

Configure TCP reception if required:

```text
module(load="imtcp")
input(type="imtcp" port="514")
```

Restart the service:

```bash
sudo systemctl restart rsyslog
```

Check the listening sockets:

```bash
sudo ss -lunpt | grep 514
```

If the server uses UFW, allow the required transport:

```bash
sudo ufw allow 514/udp
```

For TCP:

```bash
sudo ufw allow 514/tcp
```

Restrict access to trusted management networks whenever possible.

# 🗁 Storing Remote Logs in Separate Files

For better organization, remote router logs can be stored separately from other system logs.

Create a dedicated configuration file:

```bash
sudo nano /etc/rsyslog.d/20-mikrotik-storage.conf
```

Example configuration:

```text
if ($fromhost-ip == '192.168.10.1') then {
    action(type="omfile" file="/var/log/mikrotik-router.log")
    stop
}
```

This rule stores messages received from `192.168.10.1` in a dedicated file.

Restart rsyslog:

```bash
sudo systemctl restart rsyslog
```

Monitor incoming messages:

```bash
sudo tail -f /var/log/mikrotik-router.log
```

For multiple routers, create separate rules or use a structured directory and filename template based on the sender address.

Useful commands for investigating the Syslog server include:

Check service status:

```bash
sudo systemctl status rsyslog
```

Inspect service logs:

```bash
sudo journalctl -u rsyslog
```

Monitor incoming router logs:

```bash
sudo tail -f /var/log/mikrotik-router.log
```

Check UDP port listening:

```bash

```

```bash

```

If messages are not arriving, investigate:

* Router remote logging configuration.
* Syslog server address and port.
* Transport protocol compatibility.
* Routing between the router and server.
* Firewall policies.
* Server listener configuration.
* Network connectivity.

# 🗁 Logging Firewall Events

Firewall logging can help identify blocked or suspicious traffic.

Example firewall rule with logging:

```routeros
/ip/firewall/filter/add chain=input protocol=tcp dst-port=22 action=drop log=yes log-prefix="SSH-DROP "
```

This rule drops matching TCP traffic destined for port 22 on the router and logs the event.

Inspect firewall log entries:

```routeros
/log/print where topics~"firewall"
```

Firewall logging should be used selectively.

Logging every dropped packet on a busy router can generate excessive messages, increase processing overhead, and overwhelm the logging destination.

For production networks, use carefully scoped logging rules, connection limits, and appropriate log retention policies.

# 🗁 Logging PPPoE and Subscriber Events

For ISP environments, PPPoE and subscriber activity can be important for operational monitoring.

Inspect PPP-related logs:

```routeros
/log/print where topics~"ppp"
```

Potentially useful events include:

* Subscriber authentication failures.
* PPPoE session establishment.
* Session termination.
* Profile-related issues.
* RADIUS authentication problems.

Forward relevant events to a centralized Syslog server:

```routeros
/system/logging/add topics=ppp action=remote-syslog
```

Centralized subscriber logs can help correlate customer complaints with authentication events and session changes.

# 🗁 Logging Security Events

Logging is useful for detecting and investigating security-related activity.

Events worth monitoring include:

* Failed login attempts.
* Unauthorized management access.
* Firewall drops.
* Configuration changes.
* Unexpected system restarts.
* VPN authentication failures.
* Unusual subscriber activity.

For account-related events:

```routeros
/log/print where topics~"account"
```

For system-related events:

```routeros
/log/print where topics~"system"
```

For firewall events:

```routeros
/log/print where topics~"firewall"
```

A centralized logging system can correlate events from multiple routers and other infrastructure components.

# 🗁 Logging Best Practices

* Configure memory logging for immediate troubleshooting.
* Forward important events to a centralized Syslog server.
* Use dedicated logging rules for important topics.
* Avoid excessive firewall logging.
* Protect access to local and remote log storage.
* Restrict Syslog reception to trusted network devices.
* Use encrypted transport when supported and required.
* Synchronize device clocks using NTP.
* Configure log rotation and retention.
* Monitor storage consumption on the Syslog server.
* Protect logs from unauthorized modification.
* Regularly review authentication and security-related events.

# 🗁 Common Logging and Syslog Problems

| Problem | Possible Cause | Investigation |
| --- | --- | --- |
| No logs displayed locally | Incorrect logging rules or action | `/system/logging/print` |
| Remote server receives no messages | Incorrect server address or routing | Check remote action and connectivity |
| Syslog server is not listening | Service configuration problem | `ss -lunp` |
| Firewall blocks Syslog traffic | UDP or TCP port blocked | Review firewall policies |
| Logs are missing during outages | UDP delivery is not guaranteed | Review transport and connectivity |
| Log files consume excessive storage | Missing rotation or retention policy | Inspect server storage |
| Log timestamps are incorrect | NTP or timezone configuration issue | Check time synchronization |
| Too many firewall messages | Overly broad logging rules | Review firewall logging configuration |

Logging and Syslog provide an important foundation for network observability, security investigations, and centralized infrastructure management.
