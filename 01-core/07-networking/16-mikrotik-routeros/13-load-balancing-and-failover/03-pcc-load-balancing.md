# PCC Load Balancing

# 🗁 What Is PCC?

Per Connection Classifier (PCC) is a MikroTik RouterOS firewall matcher used to distribute network connections across multiple WAN links.

PCC classifies connections using selected source and destination address and port information. Each connection is assigned to a classification group, which can then be associated with a particular WAN connection.

For example, with two WAN links:

* Connections classified into group `0` use WAN-1.
* Connections classified into group `1` use WAN-2.

PCC is commonly used when an ISP, business, or network administrator wants to distribute outgoing Internet connections across multiple upstream connections.

# 🗁 How PCC Works

PCC uses a hashing process to classify connections.

The classification method determines which connection fields are used to calculate the hash.

For a two-WAN design:

```text
                    LAN Clients
                         |
                         |
                   MikroTik Router
                         |
                    PCC Classifier
                         |
                 +-------+-------+
                 |               |
              Group 0         Group 1
                 |               |
               WAN-1           WAN-2
                 |               |
               ISP-1           ISP-2
                 |               |
                 +-------+-------+
                         |
                      Internet
```

The router marks each new connection according to its PCC group. It then applies a routing mark so packets belonging to that connection use the corresponding routing table.

# 🗁 PCC Classification Methods

RouterOS supports several PCC classification combinations.

| PCC method | Classification fields |
| --- | --- |
| `src-address` | Source IP address |
| `dst-address` | Destination IP address |
| `src-port` | Source port |
| `dst-port` | Destination port |
| `src-address-and-port` | Source IP and source port |
| `dst-address-and-port` | Destination IP and destination port |
| `both-addresses` | Source and destination IP addresses |
| `both-ports` | Source and destination ports |
| `both-addresses-and-ports` | Source IP, destination IP, source port, and destination port |

The choice depends on the network's traffic distribution requirements.

For general Internet access, `both-addresses-and-ports` is commonly used because it considers multiple connection attributes.

# 🗁 Understanding PCC Divisors and Remainders

The PCC classifier uses a divisor and remainder to divide connections into groups.

General format:

```text
both-addresses-and-ports:divisor/remainder
```

For two WAN links:

```text
both-addresses-and-ports:2/0
both-addresses-and-ports:2/1
```

The divisor `2` creates two classification groups.

The remainder identifies the group:

| PCC expression | Group | WAN |
| --- | --- | --- |
| `2/0` | 0 | WAN-1 |
| `2/1` | 1 | WAN-2 |

For three WAN links:

```text
both-addresses-and-ports:3/0
both-addresses-and-ports:3/1
both-addresses-and-ports:3/2
```

For four WAN links:

```text
both-addresses-and-ports:4/0
both-addresses-and-ports:4/1
both-addresses-and-ports:4/2
both-addresses-and-ports:4/3
```

Every new connection is classified into one of the available groups.

# 🗁 Connection Marking and Routing Marking

PCC load balancing commonly uses two types of marks.

**Connection Mark**

A connection mark identifies the WAN group assigned to a connection.

Examples:

* `wan1_conn`
* `wan2_conn`

The connection mark is stored in connection tracking and remains associated with the connection.

**Routing Mark**

A routing mark selects the routing table used for packets belonging to a marked connection.

Examples:

* `to_wan1`
* `to_wan2`

The relationship is:

```text
New Connection
      |
      v
PCC Classification
      |
      v
Connection Mark
      |
      v
Routing Mark
      |
      v
Selected Routing Table
      |
      v
Selected WAN Interface
```

Connection marking and routing marking are separate operations. A connection mark alone does not select a routing table.

# 🗁 Understanding RouterOS Mangle Chains

RouterOS Mangle rules can process packets in different firewall chains.

| Chain | Purpose |
| --- | --- |
| `prerouting` | Processes packets before routing decisions |
| `input` | Processes packets destined for the router |
| `forward` | Processes packets routed through the router |
| `output` | Processes packets generated by the router |
| `postrouting` | Processes packets after routing decisions |

For LAN-originated PCC traffic, `prerouting` is commonly used because the router can classify connections and apply routing marks before making the routing decision.

Traffic generated by the router itself does not pass through `prerouting`. It requires separate handling if it must use a particular WAN.

This example uses two Internet connections.

```text
                       Internet
                      /        \
                     /          \
                  ISP-1         ISP-2
                    |             |
               192.0.2.1     198.51.100.1
                    |             |
                 ether1         ether2
                    \             /
                     \           /
                    MikroTik Router
                           |

                           |
                     LAN Network
```

Example addressing plan:

| Component | Address |
| --- | --- |
| WAN-1 interface | `ether1` |
| WAN-1 gateway | `192.0.2.1` |
| WAN-1 router address | `192.0.2.2/24` |

# 🗁 Configure WAN Interfaces

Assign the WAN addresses:

```routeros
/ip/address
add address=192.0.2.2/24 interface=ether1 comment="WAN-1"
add address=198.51.100.2/24 interface=ether2 comment="WAN-2"
```

Configure the LAN gateway:

```routeros
/ip/address
add address=192.168.10.1/24 interface=bridge comment="LAN gateway"
```

Verify the addresses:

```routeros
/ip/address/print
```

Confirm that both WAN gateways are reachable before continuing.

# 🗁 Create Routing Tables

RouterOS v7 supports custom routing tables.

Create one table for each WAN:

```routeros
/routing/table
add name=to_wan1 fib
add name=to_wan2 fib
```

The `fib` property enables the routing table to be used for forwarding.

Verify the tables:

```routeros
/routing/table/print
```

# 🗁 Configure WAN Routing

Create a default route in the main routing table:

```routeros
/ip/route
add dst-address=0.0.0.0/0 \
    gateway=192.0.2.1 \
    distance=1 \
    comment="Main default through WAN-1"
```

Add a default route for WAN-1's routing table:

```routeros
/ip/route
add dst-address=0.0.0.0/0 \
    gateway=192.0.2.1@main \
    routing-table=to_wan1 \
    distance=1 \
    comment="PCC WAN-1 route"
```

Add a default route for WAN-2's routing table:

```routeros
/ip/route
add dst-address=0.0.0.0/0 \
    gateway=198.51.100.1@main \
    routing-table=to_wan2 \
    distance=1 \
    comment="PCC WAN-2 route"
```

The `@main` notation specifies that the gateway should be resolved using the main routing table.

Verify the routes:

```routeros
/ip/route/print detail
```

Both custom routing tables need valid routes before PCC-marked traffic can use them.

# 🗁 Configure Local Network Address Lists

PCC should classify Internet-bound traffic, not traffic destined for internal networks.

Create an address list containing the local networks:

```routeros
/ip/firewall/address-list
add list=local-networks address=192.168.10.0/24 comment="LAN network"
```

Add any other internal networks that should bypass PCC, such as management VLANs, VPN subnets, and additional LAN segments.

The examples below use this list to prevent internal traffic from being assigned to a WAN routing table.

# 🗁 Configure PCC Connection Marking

Create the PCC rules in the `prerouting` chain.

First, classify new LAN connections into WAN-1:

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    connection-state=new \
    connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:2/0 \
    action=mark-connection \
    new-connection-mark=wan1_conn \
    passthrough=yes \
    comment="PCC classify WAN-1"
```

Next, classify new LAN connections into WAN-2:

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    connection-state=new \
    connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:2/1 \
    action=mark-connection \
    new-connection-mark=wan2_conn \
    passthrough=yes \
    comment="PCC classify WAN-2"
```

These rules divide eligible new connections into two groups.

The `connection-mark=no-mark` condition prevents an already classified connection from being classified again.

The `passthrough=yes` setting allows packet processing to continue to subsequent Mangle rules.

# 🗁 Apply Routing Marks

After marking connections, apply the corresponding routing marks.

For WAN-1:

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    connection-mark=wan1_conn \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    action=mark-routing \
    new-routing-mark=to_wan1 \
    passthrough=no \
    comment="Route connections through WAN-1"
```

For WAN-2:

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    connection-mark=wan2_conn \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    action=mark-routing \
    new-routing-mark=to_wan2 \
    passthrough=no \
    comment="Route connections through WAN-2"
```

These rules direct packets belonging to each marked connection into the corresponding routing table.

The `passthrough=no` setting stops further Mangle rule processing for packets that match these routing-mark rules.

# 🗁 Configure NAT for Both WAN Links

Each WAN connection needs an appropriate source NAT rule.

```routeros
/ip/firewall/nat
add chain=srcnat \
    out-interface=ether1 \
    action=masquerade \
    comment="NAT through WAN-1"

add chain=srcnat \
    out-interface=ether2 \
    action=masquerade \
    comment="NAT through WAN-2"
```

The outgoing interface determines which NAT rule applies.

WAN-1 connections are translated using WAN-1's address, while WAN-2 connections are translated using WAN-2's address.

If the ISP provides static public addresses, `action=src-nat` with the assigned address can be used instead of masquerade.

# 🗁 Understand the Complete PCC Flow

The complete process is:

```text
                  LAN Client
                      |
                      v
                New Connection
                      |
                      v
               PCC Classification
                      |
              +-------+-------+
              |               |
              v               v
          wan1_conn        wan2_conn
              |               |
              v               v
           to_wan1          to_wan2
              |               |
              v               v
        Routing Table 1  Routing Table 2
              |               |
              v               v
            WAN-1           WAN-2
              |               |
              v               v
            ISP-1           ISP-2
              |               |
              +-------+-------+
                      |
                   Internet
```

Each connection receives a connection mark and uses the corresponding routing table.

# 🗁 Understanding Traffic Distribution

PCC distributes connections according to its hash calculation.

For example:

| Connection | PCC group | WAN |
| --- | --- | --- |
| Connection A | 0 | WAN-1 |
| Connection B | 1 | WAN-2 |
| Connection C | 1 | WAN-2 |
| Connection D | 0 | WAN-1 |
| Connection E | 0 | WAN-1 |
| Connection F | 1 | WAN-2 |

The distribution is not guaranteed to be exactly equal over a small number of connections.

PCC does not divide a single connection's bandwidth across both WAN links.

For example, if a client downloads one large file over one TCP connection, that connection normally uses only one WAN.

Multiple connections from the same client can be distributed across different WAN links.

# 🗁 Weighted PCC Load Balancing

PCC can distribute connections across WAN links with different bandwidth capacities.

Suppose:

| WAN | Bandwidth | Relative weight |
| --- | ---: | ---: |
| WAN-1 | 100 Mbps | 1 |
| WAN-2 | 200 Mbps | 2 |

The desired distribution is approximately:

* One-third of classified connections through WAN-1.
* Two-thirds of classified connections through WAN-2.

Use a divisor of three:

```text
WAN-1:
both-addresses-and-ports:3/0

WAN-2:
both-addresses-and-ports:3/1
both-addresses-and-ports:3/2
```

Example PCC rules:

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    connection-state=new \
    connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:3/0 \
    action=mark-connection \
    new-connection-mark=wan1_conn \
    passthrough=yes \
    comment="Weighted PCC WAN-1"
```

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    connection-state=new \
    connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:3/1 \
    action=mark-connection \
    new-connection-mark=wan2_conn \
    passthrough=yes \
    comment="Weighted PCC WAN-2 group 1"
```

```routeros
/ip/firewall/mangle
add chain=prerouting \
    in-interface=bridge \
    dst-address-type=!local \
    dst-address-list=!local-networks \
    connection-state=new \
    connection-mark=no-mark \
    per-connection-classifier=both-addresses-and-ports:3/2 \
    action=mark-connection \
    new-connection-mark=wan2_conn \
    passthrough=yes \
    comment="Weighted PCC WAN-2 group 2"
```

The routing-mark rules and routing tables remain the same as the two-WAN example.

The resulting ratio is approximately:

```text
WAN-1: 1 group
WAN-2: 2 groups

Distribution: 1:2
```

PCC distributes connections, not bandwidth in exact proportions. Actual throughput depends on connection sizes, user behavior, and traffic patterns.

# 🗁 Handling Router-Originated Traffic

Traffic generated by the MikroTik router itself follows the `output` chain rather than the LAN `prerouting` path.

Examples include:

* DNS queries generated by the router.
* NTP synchronization.
* Router-originated pings.
* Package updates.
* Monitoring requests.
* Traffic generated by RouterOS services.

The main routing table determines the path for this traffic unless separate routing policies are configured.

If router-originated traffic must use a particular WAN, configure an appropriate routing policy in the `output` chain or use routing rules and routing tables.

Do not assume that LAN PCC rules automatically load balance traffic generated by the router.

# 🗁 Handling Incoming WAN Connections

Incoming connections require additional consideration.

For example, a customer may access a server through a port-forwarding rule on WAN-1.

The return traffic must leave through WAN-1 to preserve the connection's public source address and NAT state.

A multi-WAN configuration should identify connections arriving from each WAN and preserve their return path.

A common design is to mark incoming connections in `prerouting` based on the incoming WAN interface, then apply a routing mark to their return traffic.

This requires carefully ordered Mangle rules and appropriate routing tables. It is especially important for:

* Port forwarding.
* VPN servers.
* Remote router management.
* Publicly accessible services.
* Connections initiated from the Internet.

The basic outbound PCC configuration above does not provide complete inbound connection symmetry or port-forwarding support.

# 🗁 FastTrack Considerations

FastTrack can bypass portions of normal packet processing for eligible established connections.

This can interfere with PCC designs that depend on Mangle connection marks and routing marks.

If FastTrack is enabled, ensure that PCC-marked traffic is excluded from FastTrack.

For example, a FastTrack rule can be restricted to unmarked connections:

```routeros
/ip/firewall/filter
add chain=forward \
    action=fasttrack-connection \
    connection-state=established,related \
    connection-mark=no-mark \
    comment="FastTrack unmarked connections only"
```

The complete firewall policy must still include appropriate established and related connection acceptance rules.

Review existing FastTrack rules before adding this configuration. A broader earlier FastTrack rule may need to be modified or disabled.

# 🗁 Firewall Considerations

PCC does not replace firewall filtering.

A production router still needs an appropriate firewall policy for:

* Router input traffic.
* Forwarded subscriber traffic.
* Established and related connections.
* Invalid connections.
* Management access.
* Inter-LAN communication.
* WAN access restrictions.

Mangle rules classify and mark traffic. Filter rules determine whether traffic is allowed or dropped.

Rule order matters, particularly when combining PCC with other Mangle policies.

# 🗁 Test PCC Load Balancing

Perform the following tests:

**Test WAN-1**

* Generate multiple new connections from a LAN client.
* Inspect the connection table.
* Confirm that some connections receive `wan1_conn`.
* Verify that their traffic exits through WAN-1.

**Test WAN-2**

* Generate additional new connections.
* Inspect the connection table.
* Confirm that some connections receive `wan2_conn`.
* Verify that their traffic exits through WAN-2.

**Test multiple clients**

* Connect multiple LAN devices.
* Generate simultaneous traffic.
* Monitor both WAN interfaces.
* Compare traffic counters and throughput.

**Test single-connection behavior**

* Start one large download.
* Identify the WAN carrying that connection.
* Confirm that the single connection is not split between both WAN links.

# 🗁 Troubleshooting PCC

**All traffic uses WAN-1**

Check:

* PCC rule order.
* PCC classifier expressions.
* Mangle rule counters.
* Connection marks.
* Routing marks.
* Custom routing table routes.
* Existing connections established before the configuration was added.

**All traffic uses WAN-2**

Check whether the PCC rules or routing marks have been configured incorrectly.

Inspect the connection table and confirm that both connection marks are being assigned as intended.

**PCC marks connections but traffic cannot access the Internet**

Check:

* Custom routing table routes.
* Gateway resolution.
* WAN interface status.
* NAT rules.
* Firewall forwarding.
* Upstream connectivity.

**WAN-1 works but WAN-2 does not**

Check WAN-2 addressing, gateway reachability, the `to_wan2` routing table, and the WAN-2 NAT rule.

**Some websites or applications disconnect**

Investigate:

* Asymmetric routing.
* Incorrect NAT selection.
* Connection marking.
* FastTrack.
* Application dependencies on a stable public source IP.

**Router-generated traffic uses only one WAN**

Review the main routing table and configure a separate policy for router-originated traffic if required.

**Traffic distribution appears uneven**

Remember that PCC distributes connections, not bytes. A few large connections can make one WAN carry more bandwidth even when connection counts are balanced.

# 🗁 Best Practices

* Use connection-based distribution for ordinary Internet traffic.
* Choose the PCC classifier according to the network requirements.
* Create separate routing tables for each WAN.
* Add valid default routes to every custom routing table.
* Exclude internal destinations from PCC classification.
* Use connection marks to preserve connection-to-WAN association.
* Configure NAT for each WAN.
* Review FastTrack compatibility.
* Handle router-originated traffic separately.
* Preserve symmetric routing for incoming connections.
* Use weighted PCC when WAN capacities differ.
* Monitor both connection counts and actual throughput.
* Test new connections after changing PCC rules.
* Document connection marks, routing marks, and routing tables.
