# 🗁 Firewall Fundamentals

### 🖆 What Is a Firewall?

A firewall is a network security mechanism that controls incoming, outgoing, and forwarded traffic according to predefined security policies.

A firewall evaluates traffic using information such as:

* Source IP address.
* Destination IP address.
* Source port.
* Destination port.
* Transport protocol.
* Incoming interface.
* Outgoing interface.
* Connection state.

For example, a firewall can allow HTTP and HTTPS traffic while blocking unauthorized access to SSH.

### 🖆 Types of Firewall

| Firewall Type | Description |
| --- | --- |
| Packet-filtering firewall | Filters packets using IP addresses, protocols, and ports. |
| Stateful firewall | Tracks connection states and makes filtering decisions using connection information. |
| Stateless firewall | Evaluates packets individually without maintaining connection state. |
| Application-layer firewall | Inspects application-level traffic and protocols. |
| Next-generation firewall | Combines traditional filtering with advanced security inspection features. |

### 🖆 Stateful vs Stateless Firewall

**Stateless firewall**

* Evaluates each packet independently.
* Does not maintain connection information.
* Requires explicit rules for relevant traffic directions.

**Stateful firewall**

* Tracks active connections.
* Recognizes established and related traffic.
* Can allow return traffic based on connection state.

MikroTik RouterOS uses connection tracking to support stateful firewall filtering.

### 🖆 Firewall Chains in MikroTik

MikroTik RouterOS uses three primary filter chains:

| Chain | Purpose |
| --- | --- |
| input | Traffic destined for the router itself. |
| forward | Traffic passing through the router between networks. |
| output | Traffic generated by the router itself. |

Examples:

* Accessing a router's SSH service uses the `input` chain.
* A LAN client accessing a remote server uses the `forward` chain.
* A router sending a DNS query uses the `output` chain.

### 🖆 Firewall Actions

| Action | Description |
| --- | --- |
| accept | Allows the packet. |
| drop | Silently discards the packet. |
| reject | Discards the packet and sends a rejection response where supported. |
| log | Logs matching traffic and continues evaluating subsequent rules. |
| passthrough | Continues processing without making a final filtering decision. |

Rule order matters. RouterOS evaluates firewall rules from top to bottom within a chain. Once a terminating action matches, later rules in that chain are not evaluated for that packet.

# 🗁 Exercise: Understand Firewall Chains

### 🖆 Test the Input Chain

The input chain controls traffic destined for the router.

From PC-A, test whether the router responds to ICMP:

```bash
ping 192.168.10.1
```

On MikroTik, add a rule to block ICMP requests arriving from PC-A:

```routeros
/ip firewall filter
add chain=input src-address=192.168.10.10 protocol=icmp action=drop comment="Block PC-A ping to router"
```

Repeat the ping test.

The router should stop responding to PC-A's ICMP requests.

Remove the test rule:

```routeros
/ip firewall filter
remove [find comment="Block PC-A ping to router"]
```

### 🖆 Test the Forward Chain

The forward chain controls traffic passing through the router.

Add a rule to block PC-A from reaching PC-B:

```routeros
/ip firewall filter
add chain=forward src-address=192.168.10.10 dst-address=192.168.10.20 action=drop comment="Block PC-A to PC-B"
```

From PC-A:

```bash
ping 192.168.10.20
```

The traffic should be dropped.

Remove the test rule:

```routeros
/ip firewall filter
remove [find comment="Block PC-A to PC-B"]
```

### 🖆 Understand the Output Chain

The output chain controls traffic generated by the router itself.

For example, a router-generated ping is processed through the output chain:

```routeros
/ping 10.0.0.1
```

A test rule can block outgoing ICMP packets:

```routeros
/ip firewall filter
add chain=output protocol=icmp action=drop comment="Block router ICMP output"
```

Remove the rule after testing:

```routeros
/ip firewall filter
remove [find comment="Block router ICMP output"]
```

# 🗁 Exercise: Configure Stateful Firewall Rules

### 🖆 Understand Connection States

MikroTik connection tracking identifies traffic using connection states.

| Connection State | Description |
| --- | --- |
| new | A packet that starts a new connection. |
| established | Traffic belonging to an already established connection. |
| related | Traffic associated with an existing connection. |
| invalid | Traffic that cannot be associated with a valid connection. |
| untracked | Traffic excluded from connection tracking. |

These states help administrators build stateful firewall policies.

### 🖆 Allow Established and Related Connections

Add the following rule near the top of the appropriate filter chain:

```routeros
/ip firewall filter
add chain=input connection-state=established,related action=accept comment="Allow established and related input"
```

This allows packets belonging to existing or related connections to reach the router.

For forwarded traffic:

```routeros
/ip firewall filter
add chain=forward connection-state=established,related action=accept comment="Allow established and related forward"
```

### 🖆 Drop Invalid Connections

For input traffic:

```routeros
/ip firewall filter
add chain=input connection-state=invalid action=drop comment="Drop invalid input"
```

For forwarded traffic:

```routeros
/ip firewall filter
add chain=forward connection-state=invalid action=drop comment="Drop invalid forward"
```

Place these rules before broad accept rules that could otherwise permit the unwanted traffic.

### 🖆 Allow New LAN Connections

Allow new connections originating from the trusted LAN:

```routeros
/ip firewall filter
add chain=forward in-interface=ether2 connection-state=new action=accept comment="Allow new LAN connections"
```

This is an introductory example. In a production policy, restrict the permitted destination networks and services as required.

# 🗁 Exercise: Allow and Block Specific Ports

### 🖆 Understand Common Ports

| Service | Protocol | Port |
| --- | --- | ---: |
| SSH | TCP | 22 |
| DNS | UDP/TCP | 53 |
| HTTP | TCP | 80 |
| HTTPS | TCP | 443 |
| SMTP | TCP | 25 |
| DHCP Server | UDP | 67 |
| DHCP Client | UDP | 68 |
| NTP | UDP | 123 |

### 🖆 Allow SSH Access to the Router from a Trusted Host

Assume PC-A is the trusted management workstation.

```routeros
/ip firewall filter
add chain=input src-address=192.168.10.10 protocol=tcp dst-port=22 action=accept comment="Allow SSH from management PC"
```

Then block SSH access from other sources:

```routeros
/ip firewall filter
add chain=input protocol=tcp dst-port=22 action=drop comment="Block other SSH access"
```

Place the specific allow rule before the general drop rule.

### 🖆 Block HTTP Traffic Through the Router

To block forwarded HTTP traffic:

```routeros
/ip firewall filter
add chain=forward protocol=tcp dst-port=80 action=drop comment="Block forwarded HTTP"
```

This rule affects HTTP traffic passing through the router, not HTTP traffic destined for the router itself.

### 🖆 Allow HTTPS Traffic Through the Router

```routeros
/ip firewall filter
add chain=forward protocol=tcp dst-port=443 action=accept comment="Allow forwarded HTTPS"
```

Rule placement is important. An earlier matching drop rule can prevent this rule from being reached.

# 🗁 Exercise: Configure a Basic Router Firewall

### 🖆 Understand the Policy

A basic router input policy should:

* Allow established and related connections.
* Drop invalid connections.
* Allow management access from trusted networks.
* Allow necessary network services.
* Permit ICMP where required for diagnostics.
* Drop unauthorized access to the router.

### 🖆 Configure the Input Chain

The following example assumes that `ether2` is the trusted LAN interface.

```routeros
/ip firewall filter
add chain=input connection-state=established,related action=accept comment="Allow established and related"
add chain=input connection-state=invalid action=drop comment="Drop invalid connections"
add chain=input in-interface=ether2 protocol=icmp action=accept comment="Allow LAN ICMP"
add chain=input in-interface=ether2 protocol=tcp dst-port=22 action=accept comment="Allow LAN SSH"
add chain=input in-interface=ether2 protocol=tcp dst-port=8291 action=accept comment="Allow LAN WinBox"
add chain=input action=drop comment="Drop other input traffic"
```

This is a basic example, not a complete universal router configuration. Add any required DHCP, DNS, VPN, or other management-service allowances before the final drop rule.

### 🖆 Configure the Forward Chain

```routeros
/ip firewall filter
add chain=forward connection-state=established,related action=accept comment="Allow established and related"
add chain=forward connection-state=invalid action=drop comment="Drop invalid forwarded traffic"
add chain=forward in-interface=ether2 action=accept comment="Allow LAN forwarding"
add chain=forward action=drop comment="Drop other forwarded traffic"
```

This example permits LAN-originated forwarding and blocks other forwarded traffic. Add explicit policies for additional trusted networks and required services before the final drop rule.

### 🖆 Inspect Firewall Rules

```routeros
/ip firewall filter print
```

To view rule counters:

```routeros
/ip firewall filter print stats
```

Counters help identify which rules are matching packets.

# 🗁 Exercise: Configure Logging

### 🖆 Understand Firewall Logging

Firewall logging helps administrators investigate traffic that matches particular rules.

Useful information can include:

* Source and destination IP addresses.
* Protocol and port information.
* Firewall chain.
* Matching rule prefix.
* Packet activity.

### 🖆 Log Dropped Traffic

Add a logging rule before a final drop rule:

```routeros
/ip firewall filter
add chain=input action=log log-prefix="INPUT-DROP: " comment="Log input traffic"
```

Logging does not itself block packets. It records matching traffic and continues to the next firewall rule.

### 🖆 Drop Traffic After Logging

```routeros
/ip firewall filter
add chain=input action=drop comment="Drop remaining input traffic"
```

### 🖆 View Router Logs

```routeros
/log print
```

Use a specific log prefix to identify relevant entries.

Avoid logging every packet on a busy router. Excessive logging can consume resources and make useful events difficult to identify.

# 🗁 Exercise: Understand Connection Tracking

### 🖆 Inspect Connection Tracking

MikroTik maintains connection information for stateful firewall processing.

View active connections:

```routeros
/ip firewall connection print
```

You can inspect details such as:

* Original source and destination.
* Translated source and destination, when NAT is involved.
* Protocol.
* Connection state.
* Timeout information.

### 🖆 Observe a TCP Connection

From Ubuntu, establish an SSH connection to a test server:

```bash
ssh username@192.168.10.20
```

While the connection is active, inspect the router's connection tracking table:

```routeros
/ip firewall connection print detail
```

Observe how the router tracks the connection.

### 🖆 Disable Connection Tracking for a Test

Connection tracking is normally enabled and is required for common stateful firewall and NAT configurations.

Inspect its settings:

```routeros
/ip firewall connection tracking print
```

Avoid disabling connection tracking on a production router simply for experimentation. Instead, use an isolated lab and understand the effects on stateful filtering and NAT before changing it.

# 🗁 Exercise: Configure Address-Based Filtering

### 🖆 Block a Specific Client

Block PC-B from accessing networks through the router:

```routeros
/ip firewall filter
add chain=forward src-address=192.168.10.20 action=drop comment="Block PC-B forwarding"
```

### 🖆 Allow a Specific Client

If the general drop rule is already configured, add a specific allow rule above it:

```routeros
/ip firewall filter
add chain=forward src-address=192.168.10.10 action=accept comment="Allow PC-A forwarding"
```

### 🖆 Test the Rules

From PC-A and PC-B, test access to a reachable remote destination.

Compare the results and inspect rule counters:

```routeros
/ip firewall filter print stats
```

Remember that a rule in the forward chain affects transit traffic. Traffic destined for the router itself is handled by the input chain.

# 🗁 Exercise: Configure Interface-Based Filtering

### 🖆 Understand Interface Matching

Firewall rules can match packets according to their incoming and outgoing interfaces.

Common matching properties include:

* `in-interface`
* `out-interface`
* `in-interface-list`
* `out-interface-list`

### 🖆 Create an Interface List

Create a trusted LAN interface list:

```routeros
/interface list
add name=LAN
```

Add the LAN interface:

```routeros
/interface list member
add list=LAN interface=ether2
```

### 🖆 Allow Traffic from the LAN Interface List

```routeros
/ip firewall filter
add chain=forward in-interface-list=LAN action=accept comment="Allow LAN forwarding"
```

This makes it easier to manage multiple trusted interfaces using one interface list.

# 🗁 Linux Firewall Practice

### 🖆 Inspect the Linux Firewall

Ubuntu systems commonly use nftables as the underlying packet-filtering framework. UFW provides a simpler management interface.

Check UFW status:

```bash
sudo ufw status verbose
```

Inspect nftables rules:

```bash
sudo nft list ruleset
```

### 🖆 Allow SSH

```bash
sudo ufw allow 22/tcp
```

### 🖆 Allow HTTPS

```bash
sudo ufw allow 443/tcp
```

### 🖆 Block HTTP

```bash
sudo ufw deny 80/tcp
```

### 🖆 Delete a Firewall Rule

```bash
sudo ufw delete deny 80/tcp
```

### 🖆 Enable UFW

```bash
sudo ufw enable
```

### 🖆 Verify Firewall Rules

```bash
sudo ufw status numbered
```

UFW rules control traffic to and from the Linux host. They are not automatically equivalent to MikroTik router forwarding rules.

# 🗁 Firewall Troubleshooting Exercises

### 🖆 Problem: Traffic Is Blocked Unexpectedly

**Symptoms:**

* The routing table contains a valid route.
* The destination is reachable from the router.
* Client-to-client or client-to-server traffic fails.

**Investigation:**

```routeros
/ip firewall filter print stats
/ip firewall connection print
```

**Solution:**

Identify the matching drop or reject rule and correct its conditions or placement.

### 🖆 Problem: SSH Access Is Blocked

**Symptoms:**

* The router responds to ping.
* SSH connections time out or fail.
* Management access is unavailable.

**Investigation:**

```routeros
/ip service print
/ip firewall filter print detail
```

Check the SSH service configuration, TCP port, trusted source address, and input-chain rules.

**Solution:**

Allow SSH from the intended management network before the final input-chain drop rule.

### 🖆 Problem: Return Traffic Is Blocked

**Symptoms:**

* A client can initiate a connection.
* Responses are not received.
* Firewall rules do not permit established traffic.

**Investigation:**

```routeros
/ip firewall connection print
/ip firewall filter print stats
```

**Solution:**

Review connection tracking and ensure established and related traffic is allowed in the appropriate chain.

### 🖆 Problem: Firewall Rule Is Not Matching

**Symptoms:**

* The rule exists.
* Its packet and byte counters remain unchanged.
* Traffic behaves differently than expected.

**Investigation:**

```routeros
/ip firewall filter print detail
/ip firewall filter print stats
```

**Solution:**

Verify:

* Correct firewall chain.
* Correct source and destination addresses.
* Correct protocol and ports.
* Correct incoming and outgoing interfaces.
* Rule order.

### 🖆 Problem: Traffic Is Allowed Despite a Drop Rule

**Symptoms:**

* A drop rule exists.
* The intended traffic is still permitted.

**Investigation:**

Inspect rules above the drop rule.

**Solution:**

Move the drop rule into the correct position or correct an earlier rule that accepts the same traffic.
