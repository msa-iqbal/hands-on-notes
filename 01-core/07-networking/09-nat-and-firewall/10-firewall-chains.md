# Firewall Chains

Firewall chains are ordered sequences of rules that determine how network packets are evaluated at specific stages of packet processing.

They are fundamental to Linux Netfilter, nftables, iptables, and MikroTik RouterOS firewall configurations.

A firewall chain defines which rules are evaluated, in what order they are evaluated, and what happens when a packet matches a rule.

Understanding firewall chains is essential for building secure network policies, controlling traffic between network interfaces, protecting routers, and troubleshooting packet filtering and NAT.

# 🗁 Overview

A firewall receives packets and evaluates them against configured rules.

A chain organizes these rules into a specific processing stage or logical policy.

For example, a Linux server may have separate chains for:

| Chain | Purpose |
| --- | --- |
| `input` | Controls packets destined for the local system |
| `forward` | Controls packets routed through the system |
| `output` | Controls packets generated by the local system |
| `prerouting` | Processes incoming packets before the routing decision |
| `postrouting` | Processes packets after the routing decision |

Consider a Linux router with two interfaces:

```text
                  Internet
                     |
                     |
                  eth0 (WAN)
                     |
              +--------------+
              | Linux Router |
              |              |
              | Firewall     |
              | Netfilter    |
              +--------------+
                     |
                  eth1 (LAN)
                     |
              Internal Network
               192.168.10.0/24
```

The firewall evaluates packets according to their direction and destination.

* Traffic destined for the router reaches the `input` chain.
* Traffic passing through the router reaches the `forward` chain.
* Traffic generated by the router itself reaches the `output` chain.

# 🗁 Firewall Tables, Chains, Hooks, and Rules

Understanding these terms is important when working with Linux firewalls.

| Component | Description |
| --- | --- |
| Table | Logical container for chains and related firewall objects |
| Chain | Ordered collection of rules |
| Hook | Kernel packet-processing point where a base chain can execute |
| Rule | Defines packet matching conditions and actions |
| Priority | Determines the execution order of base chains attached to the same hook |
| Policy | Default verdict of a base chain when no rule provides a terminal verdict |
| Verdict | Determines what happens to a packet during rule evaluation |

A simplified hierarchy:

```text
Firewall Ruleset
    |
    +-- Table
          |
          +-- Base Chain
          |      |
          |      +-- Rule
          |      +-- Rule
          |      +-- Rule
          |
          +-- Regular Chain
                 |
                 +-- Rule
                 +-- Rule
```

A table is a logical organizational container. It is not itself a packet-processing hook.

A base chain attaches to a kernel hook and receives packets at that processing stage.

A regular chain is reached through a jump or goto operation from another chain.

# 🗁 Linux Netfilter Hooks

Netfilter provides packet-processing hooks in the Linux networking stack.

The five commonly used IPv4 and IPv6 hooks are:

| Hook | Purpose |
| --- | --- |
| `prerouting` | Processes incoming packets before routing |
| `input` | Processes packets destined for the local system |
| `forward` | Processes packets routed through the system |
| `output` | Processes locally generated packets |
| `postrouting` | Processes packets after routing and before transmission |

**PREROUTING**

The `prerouting` hook processes incoming packets before the routing decision.

Typical uses:

* Destination NAT.
* Packet marking.
* Early packet filtering.
* Routing-related modifications.

Example:

```text
External Client
      |
      v
Network Interface
      |
      v
PREROUTING
      |
      v
Routing Decision
```

**INPUT**

The `input` hook processes packets destined for the local system.

Typical uses:

* SSH access control.
* Web server access control.
* DNS server access control.
* ICMP filtering.
* Router management restrictions.

Example:

```text
Incoming Packet
      |
      v
PREROUTING
      |
      v
Routing Decision
      |
      v
INPUT
      |
      v
Local Application
```

**FORWARD**

The `forward` hook processes packets routed through the Linux system.

Typical uses:

* LAN-to-WAN traffic control.
* Inter-VLAN filtering.
* Network segmentation.
* Router firewall policies.
* Traffic restrictions between subnets.

Example:

```text
LAN Interface
      |
      v
PREROUTING
      |
      v
Routing Decision
      |
      v
FORWARD
      |
      v
POSTROUTING
      |
      v
WAN Interface
```

**OUTPUT**

The `output` hook processes packets generated locally by the Linux system.

Typical uses:

* Restricting outbound connections.
* Controlling locally generated DNS traffic.
* Filtering application traffic.
* Applying packet marks.

Example:

```text
Local Application
      |
      v
OUTPUT
      |
      v
Routing Decision
      |
      v
POSTROUTING
      |
      v
Network Interface
```

**POSTROUTING**

The `postrouting` hook processes packets after the routing decision and before they leave the system.

Typical uses:

* Source NAT.
* Masquerading.
* Packet marking.
* Final packet modifications before transmission.

Example:

```text
Routing Decision
      |
      v
POSTROUTING
      |
      v
Source NAT
      |
      v
Outgoing Interface
```

# 🗁 Packet Processing Paths

The Linux networking stack processes packets differently depending on whether they are locally received, forwarded, or locally generated.

**Incoming traffic destined for the local system**

```text
Network Interface
      |
      v
PREROUTING
      |
      v
Routing Decision
      |
      v
INPUT
      |
      v
Local Process
```

Example: An external client connects to an SSH server running on the Linux router.

**Incoming traffic forwarded through the system**

```text
Incoming Interface
      |
      v
PREROUTING
      |
      v
Routing Decision
      |
      v
FORWARD
      |
      v
POSTROUTING
      |
      v
Outgoing Interface
```

Example: A workstation accesses a website through a Linux router.

**Locally generated traffic**

```text
Local Process
      |
      v
OUTPUT
      |
      v
Routing Decision
      |
      v
POSTROUTING
      |
      v
Outgoing Interface
```

Example: A Linux server sends an HTTP request to an external API.

These paths are important when selecting the correct chain for a firewall rule.

A rule placed in `input` does not control ordinary traffic forwarded between two interfaces. That traffic must be evaluated through `forward`.

# 🗁 Types of nftables Chains

nftables supports base chains and regular chains.

Base chains attach to Netfilter hooks and process packets at specific stages.

Regular chains organize rules and are invoked from other chains.

A base chain has a type, hook, priority, and optionally a policy.

The commonly used base chain types are:

| Type | Purpose |
| --- | --- |
| `filter` | Packet filtering |
| `nat` | Network address translation |
| `route` | Re-evaluates routing for relevant locally generated packets when packet properties change |

**Filter chains**

Filter chains implement packet filtering.

Example:

```nft
table inet filter {
    chain input {
        type filter hook input priority filter;
        policy drop;

        iifname "lo" accept
        ct state established,related accept
        tcp dport 22 accept
    }
}
```

**NAT chains**

NAT chains implement source and destination address translation.

Example:

```nft
table ip nat {
    chain prerouting {
        type nat hook prerouting priority dstnat;
        policy accept;

        tcp dport 8080 dnat to 192.168.10.100:80
    }

    chain postrouting {
        type nat hook postrouting priority srcnat;
        policy accept;

        oifname "eth0" masquerade
    }
}
```

Stateful NAT normally establishes its mapping using the first packet of a connection. Connection tracking applies the mapping to subsequent packets.

**Route chains**

Route-type chains are primarily relevant to the output hook.

They allow routing to be reconsidered when relevant packet properties, such as marks, are changed.

Example:

```nft
table inet route_policy {
    chain output {
        type route hook output priority mangle;
        policy accept;

        ip daddr 192.0.2.0/24 meta mark set 10
    }
}
```

The actual policy-routing behavior also depends on routing rules and routing tables configured in the operating system.

# 🗁 nftables Families

nftables supports multiple protocol families.

| Family | Purpose |
| --- | --- |
| `ip` | IPv4 packet filtering and NAT |
| `ip6` | IPv6 packet filtering and NAT |
| `inet` | Combined IPv4 and IPv6 processing |
| `arp` | ARP packet processing |
| `bridge` | Ethernet bridge traffic filtering |
| `netdev` | Network device ingress and egress processing |

**IPv4 family**

```bash
sudo nft add table ip filter
```

**IPv6 family**

```bash
sudo nft add table ip6 filter
```

**Combined IPv4 and IPv6 family**

```bash
sudo nft add table inet filter
```

The `inet` family is useful for systems that need a common firewall policy for IPv4 and IPv6.

Protocol-specific expressions can still be used to apply different rules to each protocol.

For example:

```nft
table inet filter {
    chain input {
        type filter hook input priority filter;
        policy drop;

        ip protocol icmp accept
        ip6 nexthdr ipv6-icmp accept
    }
}
```

For production IPv6 policies, ensure that necessary ICMPv6 traffic is allowed, including Neighbor Discovery and Packet Too Big messages.

# 🗁 Rule Evaluation and Verdicts

Firewall rules are evaluated sequentially within a chain.

Each rule contains matching expressions and one or more statements.

When a packet matches a rule, the configured verdict or action determines how processing continues.

Common nftables verdicts:

| Verdict | Description |
| --- | --- |
| `accept` | Accepts the packet at the current hook |
| `drop` | Discards the packet silently |
| `reject` | Discards the packet and sends an appropriate error response where possible |
| `jump` | Transfers evaluation to another chain and returns to the calling chain when that chain returns |
| `goto` | Transfers evaluation to another chain without creating the normal jump return point |
| `return` | Returns from a regular chain or applies the base chain policy |
| `queue` | Sends the packet to a userspace queue |
| `continue` | Continues evaluating subsequent statements and rules |

**Accept**

```nft
tcp dport 22 accept
```

Accepts matching TCP packets at the current hook.

An important distinction: `accept` in one base chain does not necessarily prevent another base chain attached to the same hook, or a later hook, from evaluating the packet.

**Drop**

```nft
ip saddr 198.51.100.25 drop
```

Silently discards packets from the specified source address.

**Reject**

```nft
tcp dport 23 reject with tcp reset
```

Rejects matching TCP traffic and sends a TCP reset.

**Jump**

```nft
jump tcp_services
```

Transfers evaluation to a regular chain. When that chain returns, evaluation continues after the jump in the calling chain.

**Goto**

```nft
goto tcp_services
```

Transfers evaluation to another chain without creating the same return point as `jump`.

**Return**

```nft
return
```

Returns from a regular chain to its caller. In a base chain, it ends evaluation of that chain and applies its policy.

**Continue**

```nft
tcp dport 80 counter continue
```

Continues processing subsequent rules after executing the counter statement.

**Queue**

```nft
queue
```

Sends matching packets to userspace through the Netfilter queue mechanism when a suitable userspace consumer is configured.

# 🗁 Base Chains and Regular Chains

A base chain is directly connected to a Netfilter hook.

A regular chain is not directly connected to a hook.

**Base chain example**

```nft
table inet filter {
    chain input {
        type filter hook input priority filter;
        policy drop;
    }
}
```

This chain receives packets destined for the local system.

**Regular chain example**

```nft
table inet filter {
    chain tcp_services {
        tcp dport 22 accept
        tcp dport 443 accept
    }

    chain input {
        type filter hook input priority filter;
        policy drop;

        jump tcp_services
    }
}
```

The `input` base chain calls `tcp_services`.

If a packet matches a service rule and is accepted, evaluation ends at that hook. If it reaches the end of the regular chain without a terminal verdict, it returns to the calling chain.

Regular chains help organize large firewall configurations into smaller logical policies.

# 🗁 Chain Priority

When multiple base chains attach to the same hook, their priority values determine their relative execution order.

Lower numerical priority values execute before higher values.

Common nftables priority names include:

| Priority name | Numerical value | Typical purpose |
| --- | ---: | --- |
| `raw` | -300 | Early processing before connection tracking |
| `mangle` | -150 | Packet modification and marking |
| `dstnat` | -100 | Destination NAT |
| `filter` | 0 | Packet filtering |
| `security` | 50 | Security-related processing |
| `srcnat` | 100 | Source NAT |

These names are convenient representations of numerical priorities.

For example:

```nft
chain prerouting {
    type nat hook prerouting priority dstnat;
    policy accept;
}
```

The chain uses the standard destination NAT priority.

A custom numerical priority can also be specified:

```nft
chain input {
    type filter hook input priority -10;
    policy accept;
}
```

Care is required when multiple base chains share a hook.

* Earlier chains can modify packet metadata used by later chains.
* A drop verdict prevents the packet from continuing through the normal path.
* An accept verdict in one base chain does not guarantee that later base chains will accept it.
* NAT chain priority affects when translation rules are evaluated.

Do not assign arbitrary priorities without understanding the other packet-processing components attached to the same hook.

# 🗁 Working with nftables Chains

The following commands are useful when managing nftables chains.

**List all tables**

```bash
sudo nft list tables
```

**List all chains**

```bash
sudo nft list chains
```

**Display the complete ruleset**

```bash
sudo nft list ruleset
```

**Display a specific table**

```bash
sudo nft list table inet filter
```

**Create a table**

```bash
sudo nft add table inet filter
```

**Create a base chain**

```bash
sudo nft add chain inet filter input \
    '{ type filter hook input priority filter; policy drop; }'
```

**Create a regular chain**

```bash
sudo nft add chain inet filter tcp_services
```

**Add a rule**

```bash
sudo nft add rule inet filter input \
    tcp dport 443 accept
```

**List a chain with handles**

```bash
sudo nft -a list chain inet filter input
```

**Delete a rule using its handle**

```bash
sudo nft delete rule inet filter input handle 5
```

Use the actual handle displayed by the listing command.

**Flush a chain**

```bash
sudo nft flush chain inet filter input
```

Flushing removes the chain's rules but does not remove the chain itself.

**Delete a chain**

```bash
sudo nft delete chain inet filter tcp_services
```

A chain must not still be referenced by other rules when deleting it.

# 🗁 Example Linux Firewall Configuration

The following example demonstrates a basic Ubuntu/Linux host firewall using nftables.

Assumptions:

| Component | Value |
| --- | --- |
| WAN interface | `eth0` |
| Management subnet | `192.168.10.0/24` |
| SSH port | TCP 22 |
| Web service | TCP 80 and 443 |
| Firewall family | `inet` |

The policy:

* Allows loopback traffic.
* Allows established and related connections.
* Drops invalid connection-tracking states.
* Allows necessary ICMP traffic.
* Allows SSH only from the management subnet.
* Allows HTTP and HTTPS connections.
* Drops other unsolicited inbound traffic.
* Does not restrict outbound traffic in this example.

Example configuration:

```nft
table inet filter {
    chain input {
        type filter hook input priority filter;
        policy drop;

        iifname "lo" accept

        ct state invalid drop
        ct state established,related accept

        ip protocol icmp accept
        meta l4proto ipv6-icmp accept

        ip saddr 192.168.10.0/24 tcp dport 22 accept

        tcp dport { 80, 443 } accept
    }

    chain forward {
        type filter hook forward priority filter;
        policy drop;

        ct state invalid drop
        ct state established,related accept
    }

    chain output {
        type filter hook output priority filter;
        policy accept;
    }
}
```

Save the configuration in:

```text
/etc/nftables.conf
```

Validate it:

```bash
sudo nft -c -f /etc/nftables.conf
```

Apply it:

```bash
sudo nft -f /etc/nftables.conf
```

Enable the nftables service:

```bash
sudo systemctl enable --now nftables
```

Inspect the active ruleset:

```bash
sudo nft list ruleset
```

**Important configuration considerations**

* This example is a host firewall, not a complete internet gateway configuration.
* It does not enable IP forwarding.
* Its forward chain drops all forwarded traffic.
* It permits SSH only from the specified management subnet.
* If the current SSH connection originates outside that subnet, applying this configuration can disconnect the administrator.
* Preserve console or out-of-band access and verify the actual management source address before applying a restrictive policy remotely.
* ICMPv6 requires additional consideration in production. Do not indiscriminately block Neighbor Discovery, Router Advertisements where applicable, or Packet Too Big messages.

# 🗁 Custom Chains

Custom chains organize firewall rules by purpose.

For example, a firewall may use separate chains for:

* SSH management.
* Web services.
* DNS traffic.
* VPN traffic.
* Trusted networks.
* Untrusted networks.

Example:

```nft
table inet filter {
    chain input {
        type filter hook input priority filter;
        policy drop;

        iifname "lo" accept
        ct state established,related accept
        ct state invalid drop

        jump management_services
        jump web_services
    }

    chain management_services {
        ip saddr 192.168.10.0/24 tcp dport 22 accept
        return
    }

    chain web_services {
        tcp dport { 80, 443 } accept
        return
    }
}
```

The `input` chain delegates service-specific filtering to the custom chains.

This improves readability and makes complex policies easier to maintain.

# 🗁 iptables Chains

iptables uses predefined chains organized within separate tables.

The most commonly used tables are:

| Table | Purpose |
| --- | --- |
| `filter` | Packet filtering |
| `nat` | Network address translation |
| `mangle` | Packet modification |
| `raw` | Connection-tracking exceptions and early processing |
| `security` | Security-related packet processing |

**Filter table chains**

| Chain | Purpose |
| --- | --- |
| `INPUT` | Traffic destined for the local system |
| `FORWARD` | Traffic routed through the system |
| `OUTPUT` | Traffic generated by the local system |

**NAT table chains**

| Chain | Purpose |
| --- | --- |
| `PREROUTING` | Destination NAT for incoming traffic before routing |
| `INPUT` | Destination NAT for locally destined traffic, where supported |
| `OUTPUT` | Destination NAT for locally generated traffic |
| `POSTROUTING` | Source NAT before outgoing transmission |

**Common iptables commands**

List filter rules:

```bash
sudo iptables -L -n -v
```

List NAT rules:

```bash
sudo iptables -t nat -L -n -v
```

Append a rule to INPUT:

```bash
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT
```

Append a rule to FORWARD:

```bash
sudo iptables -A FORWARD -p tcp --dport 443 -j ACCEPT
```

Append a rule to OUTPUT:

```bash
sudo iptables -A OUTPUT -p tcp --dport 443 -j ACCEPT
```

Display rules with line numbers:

```bash
sudo iptables -L -n -v --line-numbers
```

Delete a rule by line number:

```bash
sudo iptables -D INPUT 1
```

iptables rules are evaluated in order. The first matching terminal verdict determines the result within that chain.

The `iptables` command on modern Ubuntu installations may use the nftables compatibility backend, often identified as `iptables-nft`.

For new Linux firewall configurations, nftables is generally the preferred interface.

# 🗁 MikroTik RouterOS Firewall Chains

MikroTik RouterOS uses firewall chains to organize filter, NAT, and other firewall rules.

The main filter chains are:

| Chain | Purpose |
| --- | --- |
| `input` | Traffic destined for the router itself |
| `forward` | Traffic passing through the router |
| `output` | Traffic generated by the router |

The NAT facility uses:

| Chain | Purpose |
| --- | --- |
| `srcnat` | Source NAT |
| `dstnat` | Destination NAT |

**Input chain**

Controls access to the router itself.

Examples:

* WinBox management.
* SSH access.
* WebFig access.
* Router DNS service.
* Router ICMP responses.

Example:

```routeros
/ip firewall filter add \
    chain=input \
    connection-state=established,related \
    action=accept \
    comment="Allow established and related"
```

**Forward chain**

Controls traffic passing through the router.

Examples:

* LAN-to-WAN access.
* Inter-VLAN communication.
* Port-forwarded connections.
* Guest network restrictions.
* VPN client traffic.

Example:

```routeros
/ip firewall filter add \
    chain=forward \
    connection-state=established,related \
    action=accept \
    comment="Allow established and related"
```

**Output chain**

Controls traffic generated by the router.

Examples:

* DNS queries from the router.
* NTP synchronization.
* Router software updates.
* Monitoring traffic.

Example:

```routeros
/ip firewall filter add \
    chain=output \
    protocol=icmp \
    action=accept \
    comment="Allow router ICMP traffic"
```

**Custom chains**

RouterOS supports custom chains through jump actions.

Example:

```routeros
/ip firewall filter add \
    chain=input \
    action=jump \
    jump-target=management
```

Create a rule inside the custom chain:

```routeros
/ip firewall filter add \
    chain=management \
    protocol=tcp \
    dst-port=22 \
    src-address=192.168.10.0/24 \
    action=accept
```

Return from the custom chain:

```routeros
/ip firewall filter add \
    chain=management \
    action=return
```

The custom chain must be referenced by an appropriate built-in chain to process packets.

**Inspect firewall chains and rules**

```routeros
/ip firewall filter print
```

```routeros
/ip firewall filter print stats
```

```routeros
/ip firewall nat print stats
```

```routeros
/ip firewall raw print
```

```routeros
/ip firewall mangle print
```

RouterOS evaluates rules from top to bottom. Actions such as `accept`, `drop`, `reject`, `jump`, and `return` affect how evaluation continues. Actions such as `log` generally perform their operation and allow subsequent rule evaluation.

The NAT chains `srcnat` and `dstnat` are not filter chains. They perform address translation rather than serving as the router's ordinary packet-acceptance policy.

# 🗁 Cisco ACLs and Interface Direction

Cisco IOS Access Control Lists (ACLs) provide ordered packet-filtering entries.

They are conceptually similar to firewall rule lists, but Cisco ACLs are not Linux-style Netfilter chains.

ACLs are commonly applied to interfaces in an inbound or outbound direction.

**Inbound ACL**

Evaluates packets as they enter an interface.

```text
Incoming Packet
      |
      v
Interface
      |
      v
Inbound ACL
      |
      v
Routing Decision
```

**Outbound ACL**

Evaluates packets before they leave an interface.

```text
Routing Decision
      |
      v
Outbound ACL
      |
      v
Interface
      |
      v
Outgoing Packet
```

Example named extended ACL:

```cisco
ip access-list extended LAN-IN
 permit tcp 192.168.10.0 0.0.0.255 any eq 443
 permit udp 192.168.10.0 0.0.0.255 any eq 53
 deny ip any any
```

Apply it inbound:

```cisco
interface GigabitEthernet0/0
 ip access-group LAN-IN in
```

Important ACL characteristics:

* Entries are evaluated in order.
* The first matching entry determines the ACL result.
* An implicit deny exists at the end of an ACL.
* Standard ACLs primarily match source IPv4 addresses.
* Extended ACLs can match source, destination, protocol, and transport ports.
* Named ACLs provide more manageable configuration.

Cisco ACLs and Linux firewall chains solve related filtering problems but use different processing models.

# 🗁 Best Practices

* Use separate chains for input, forward, and output traffic.
* Use default-drop policies where appropriate.
* Allow established and related traffic before general drop rules.
* Drop invalid connection-tracking states.
* Restrict router management access to trusted networks.
* Keep NAT and filtering policies logically separate.
* Use custom chains to organize large rule sets.
* Use meaningful table, chain, and rule names.
* Understand packet-processing hooks before placing rules.
* Review chain priorities when multiple base chains share a hook.
* Preserve necessary ICMP and ICMPv6 traffic.
* Validate nftables configurations before applying them.
* Maintain console or out-of-band access when changing remote firewall policies.
* Document the purpose and scope of each firewall rule.
* Monitor rule counters and firewall logs.

# 🗁 Common Mistakes

| Mistake | Explanation |
| --- | --- |
| Using `input` to filter forwarded traffic | Transit traffic is evaluated by `forward` |
| Using `forward` for traffic destined for the router | Local traffic is evaluated by `input` |
| Confusing tables with chains | Tables organize objects; chains define processing stages or policies |
| Confusing hooks with chains | Hooks are kernel processing points; base chains attach to them |
| Ignoring rule order | Earlier matching terminal verdicts affect later evaluation |
| Assuming accept bypasses every firewall chain | Other base chains or later hooks may still evaluate the packet |
| Applying NAT in the wrong chain | Destination and source NAT generally belong at different packet-processing stages |
| Ignoring chain priority | Base chains may execute in an unexpected order |
| Forgetting default policy | Unmatched packets may be accepted or dropped unexpectedly |
| Treating RouterOS NAT chains as filter chains | `srcnat` and `dstnat` perform address translation |
| Treating Cisco ACLs as Linux hooks | Cisco ACLs are applied to interfaces or other supported features |
| Applying restrictive rules remotely without recovery access | Administrative access may be lost |

# 🗁 Summary

Firewall chains organize packet-filtering and network-processing rules into ordered sequences.

In Linux Netfilter, base chains attach to hooks such as `prerouting`, `input`, `forward`, `output`, and `postrouting`.

nftables uses tables, chains, rules, priorities, and verdicts to control packet processing.

iptables provides traditional built-in chains such as `INPUT`, `FORWARD`, and `OUTPUT`.

MikroTik RouterOS uses `input`, `forward`, and `output` for filtering, and `srcnat` and `dstnat` for NAT.

Cisco ACLs provide a related filtering mechanism through ordered entries applied to interfaces or other supported features.

Remember these key points:

* A table is a logical container.
* A chain is an ordered collection of rules.
* A hook is a kernel packet-processing point.
* A base chain attaches to a hook.
* A regular chain is invoked by another chain.
* Rule order matters.
* Chain priority controls the relative order of base chains at the same hook.
* `input` handles local traffic.
* `forward` handles transit traffic.
* `output` handles locally generated traffic.
* NAT and filtering are related but separate operations.
