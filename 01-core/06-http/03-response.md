# HTTP Responses

An HTTP response is a message sent by a server to a client after receiving and processing an HTTP request.

It communicates the result of the requested operation and may contain resource data, metadata, or instructions for the client.

For example, when a browser requests a webpage, the server may return an HTML document with a `200 OK` status code. When an API receives a request to create a user, it may return a `201 Created` response containing the newly created user's information.

An HTTP response typically contains:

* HTTP version or protocol response metadata.
* Status code.
* Response headers.
* An optional response body.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

{
    "id": 1,
    "name": "Alice",
    "email": "alice@example.com"
}
```

Understanding HTTP responses is essential for frontend development, backend development, API integration, debugging, and application performance.

# 🗁 What Is an HTTP Response?

An HTTP response is a message generated by a server in response to an HTTP request.

The server processes the request and returns information describing the outcome.

A response can contain:

* HTML documents.
* JSON data.
* XML documents.
* Plain text.
* Images.
* Videos.
* Downloadable files.
* Error information.
* Redirect instructions.

For example, a client requests a user resource:

```http
GET /api/users/10 HTTP/1.1
Host: example.com
Accept: application/json
```

The server returns:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 10,
    "name": "Alice",
    "email": "alice@example.com"
}
```

The response communicates that:

* The request was successfully processed.
* The response contains JSON.
* The requested user information is available.

# 🗁 HTTP Response Structure

An HTTP/1.1 response message consists of:

* Status line.
* Response headers.
* Empty line.
* Optional response body.

General structure:

```text
Status Line
Response Headers

Optional Response Body
```

Example:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/users/25
Cache-Control: no-cache

{
    "id": 25,
    "name": "Alice",
    "email": "alice@example.com"
}
```

| Component | Description |
| --- | --- |
| Status line | Contains HTTP version, status code, and reason phrase |
| Headers | Provide response metadata |
| Empty line | Separates headers from the body |
| Response body | Contains optional response content |

HTTP/2 and HTTP/3 use binary framing rather than the textual HTTP/1.1 response format. Their response status is represented through the `:status` pseudo-header.

# 🗁 Status Line

The status line is the first line of an HTTP/1.1 response.

General syntax:

```text
HTTP-VERSION STATUS-CODE REASON-PHRASE
```

Example:

```http
HTTP/1.1 200 OK
```

It contains three components.

### 🖆 HTTP Version

Identifies the HTTP version in the HTTP/1.1 message format.

Example:

```text
HTTP/1.1
```

### 🖆 Status Code

A three-digit number representing the result of processing the request.

Example:

```text
200
```

### 🖆 Reason Phrase

A human-readable description associated with the status code.

Example:

```text
OK
```

The reason phrase is part of HTTP/1.1's textual status line. It is not a required semantic component of HTTP/2 or HTTP/3.

# 🗁 HTTP Status Codes

HTTP status codes communicate the result of processing a request.

They are divided into five categories.

| Category | Range | Meaning |
| --- | --- | --- |
| Informational | 100–199 | Request processing information |
| Successful | 200–299 | Request successfully processed |
| Redirection | 300–399 | Further action or navigation required |
| Client Error | 400–499 | Problem with the request |
| Server Error | 500–599 | Server failed to fulfill the request |

### 🖆 Informational Responses

These responses indicate that the request has been received and the process is continuing or provide other preliminary information.

Common examples:

| Status Code | Name | Description |
| --- | --- | --- |
| `100` | Continue | Client may continue sending the request |
| `101` | Switching Protocols | Server agrees to switch protocols |
| `102` | Processing | Request is being processed |
| `103` | Early Hints | Provides preliminary response information |

Example:

```http
HTTP/1.1 100 Continue
```

### 🖆 Successful Responses

These responses indicate that the request was successfully processed.

| Status Code | Name | Description |
| --- | --- | --- |
| `200` | OK | Request succeeded |
| `201` | Created | Resource was created |
| `202` | Accepted | Request accepted for processing |
| `204` | No Content | Request succeeded without response content |
| `206` | Partial Content | Server returned part of a resource |

Example:

```http
HTTP/1.1 201 Created
Content-Type: application/json

{
    "id": 25,
    "name": "Alice"
}
```

### 🖆 Redirection Responses

These responses indicate that the client may need to perform additional navigation or use another resource location.

| Status Code | Name | Description |
| --- | --- | --- |
| `301` | Moved Permanently | Resource has a permanent new location |
| `302` | Found | Temporary redirection |
| `303` | See Other | Retrieve another resource, commonly using GET |
| `304` | Not Modified | Cached representation can be reused |
| `307` | Temporary Redirect | Temporary redirect preserving the method |
| `308` | Permanent Redirect | Permanent redirect preserving the method |

Example:

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-page
```

### 🖆 Client Error Responses

These responses indicate that the request cannot be fulfilled because of a client-side issue or related request condition.

| Status Code | Name | Description |
| --- | --- | --- |
| `400` | Bad Request | Invalid request |
| `401` | Unauthorized | Valid authentication credentials are missing or invalid |
| `403` | Forbidden | Server refuses the request |
| `404` | Not Found | Resource not found |
| `405` | Method Not Allowed | HTTP method is not supported for the target resource |
| `409` | Conflict | Request conflicts with the current resource state |
| `415` | Unsupported Media Type | Request content format is unsupported |
| `422` | Unprocessable Content | Request content cannot be processed |
| `429` | Too Many Requests | Client has sent too many requests |

Example:

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
    "error": "User not found"
}
```

### 🖆 Server Error Responses

These responses indicate that the server failed to fulfill an otherwise valid request.

| Status Code | Name | Description |
| --- | --- | --- |
| `500` | Internal Server Error | Unexpected server failure |
| `501` | Not Implemented | Server does not support the requested functionality |
| `502` | Bad Gateway | Gateway received an invalid upstream response |
| `503` | Service Unavailable | Server temporarily cannot handle the request |
| `504` | Gateway Timeout | Gateway did not receive a timely upstream response |

Example:

```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{
    "error": "Internal server error"
}
```

Status codes are covered in detail in `06-status-codes.md`.

# 🗁 Response Headers

Response headers provide metadata about the server's response.

They describe information such as:

* Response content type.
* Content length.
* Caching instructions.
* Resource location.
* Cookies.
* Security policies.
* Content encoding.
* Server information.

### 🖆 Common Response Headers

| Header | Purpose |
| --- | --- |
| `Content-Type` | Describes the response body media type |
| `Content-Length` | Indicates the message body length in octets when applicable |
| `Content-Encoding` | Identifies the content coding applied to the representation |
| `Cache-Control` | Defines caching directives |
| `ETag` | Provides a representation validator |
| `Last-Modified` | Indicates when the representation was last modified |
| `Location` | Identifies a resource location, commonly for redirects |
| `Set-Cookie` | Instructs the client to store a cookie |
| `Vary` | Identifies request headers that influence response selection |
| `Access-Control-Allow-Origin` | Indicates permitted origins for browser cross-origin access |
| `Strict-Transport-Security` | Defines browser HTTPS enforcement policy |
| `Content-Security-Policy` | Defines browser content-loading security policies |

### 🖆 Example Response Headers

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 42
Cache-Control: public, max-age=3600
ETag: "abc123"

{
    "message": "Hello, World!"
}
```

The headers provide metadata that helps the client understand and process the response.

# 🗁 Response Body

The response body contains the representation or content returned by the server.

It may contain text, structured data, or binary content.

### 🖆 HTML Response

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html>
<head>
    <title>Home</title>
</head>
<body>
    <h1>Welcome</h1>
</body>
</html>
```

### 🖆 JSON Response

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 1,
    "name": "Alice",
    "role": "developer"
}
```

### 🖆 Plain Text Response

```http
HTTP/1.1 200 OK
Content-Type: text/plain

Hello from the server.
```

### 🖆 XML Response

```http
HTTP/1.1 200 OK
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<user>
    <id>1</id>
    <name>Alice</name>
</user>
```

### 🖆 Binary Response

HTTP can return binary resources such as:

* PNG images.
* JPEG images.
* PDF documents.
* ZIP archives.
* Audio files.
* Video files.

The body does not need to be human-readable text.

### 🖆 Responses Without a Body

Some HTTP responses do not contain response content.

Examples include:

* `HEAD` responses.
* `204 No Content`.
* `304 Not Modified`.
* Responses to successful `CONNECT` requests after the tunnel is established.

A `HEAD` response generally carries the same headers that a corresponding GET response would have, but no response content.

A `204` response indicates successful processing without response content.

A `304` response indicates that the client can reuse its stored representation when the relevant cache conditions are satisfied.

# 🗁 Content-Type

The `Content-Type` response header identifies the media type of the returned representation.

Example:

```http
Content-Type: application/json
```

This tells the client that the response contains JSON data.

### 🖆 Common Content Types

| Content-Type | Description |
| --- | --- |
| `text/html` | HTML document |
| `text/css` | CSS stylesheet |
| `text/javascript` | JavaScript |
| `application/json` | JSON data |
| `application/xml` | XML data |
| `text/plain` | Plain text |
| `image/png` | PNG image |
| `image/jpeg` | JPEG image |
| `application/pdf` | PDF document |
| `application/zip` | ZIP archive |
| `application/octet-stream` | Generic binary data |

### 🖆 Content-Type with Character Encoding

For text-based representations, a character encoding parameter may be included.

Example:

```http
Content-Type: text/html; charset=utf-8
```

UTF-8 is widely used for modern web content.

### 🖆 Why Content-Type Matters

The client uses the media type to determine how to interpret the response representation.

For example:

* `application/json` can be parsed as JSON.
* `text/html` can be interpreted as an HTML document.
* `image/png` identifies PNG image data.

Servers should return the correct media type for each representation.

# 🗁 Content-Length

The `Content-Length` response header indicates the length of the message content in octets when applicable.

Example:

```http
HTTP/1.1 200 OK
Content-Type: text/plain
Content-Length: 21

Hello from the server.
```

The value represents the number of octets, not necessarily the number of characters.

For example, UTF-8 characters can require more than one octet.

### 🖆 Content-Length in Practice

It is useful for:

* Determining the size of a response.
* Detecting whether a complete message has been received.
* Displaying download progress.
* Managing message framing in HTTP/1.1.

### 🖆 Important Considerations

* Do not assume every response contains `Content-Length`.
* HTTP/1.1 can use chunked transfer coding when the message length is not known in advance.
* HTTP/2 and HTTP/3 use their own frame-based message boundaries.
* Content compression can change the transmitted size.

# 🗁 Location Header

The `Location` response header identifies a resource location.

It is commonly used with redirection responses and resource creation responses.

### 🖆 Redirect Example

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-page
```

The client is informed that the resource has moved permanently.

### 🖆 Resource Creation Example

```http
HTTP/1.1 201 Created
Location: /api/users/25
Content-Type: application/json

{
    "id": 25,
    "name": "Alice"
}
```

The `Location` header identifies the newly created resource.

# 🗁 Set-Cookie Header

The `Set-Cookie` response header instructs a client to store a cookie.

Example:

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax
Content-Type: text/plain

Login successful.
```

The browser stores the cookie according to its attributes and applicable browser policies.

Important cookie attributes include:

| Attribute | Purpose |
| --- | --- |
| `Expires` | Specifies an expiration date |
| `Max-Age` | Specifies the cookie lifetime |
| `Domain` | Controls the domain scope |
| `Path` | Controls the URL path scope |
| `Secure` | Restricts transmission to secure connections |
| `HttpOnly` | Prevents access through JavaScript cookie APIs |
| `SameSite` | Controls cross-site cookie sending behavior |

Cookies are covered in detail in `07-cookies.md`.

# 🗁 Cache-Control Header

The `Cache-Control` response header defines caching directives for browsers and intermediary caches.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=3600

{
    "message": "Cached response"
}
```

Common directives include:

| Directive | Purpose |
| --- | --- |
| `public` | Allows shared caches to store the response |
| `private` | Restricts storage to private caches |
| `no-cache` | Requires validation before reuse |
| `no-store` | Prohibits storing the response |
| `max-age` | Defines freshness lifetime |
| `must-revalidate` | Requires revalidation after the response becomes stale |

Example:

```http
Cache-Control: private, max-age=300
```

This allows a private cache to reuse the response while it remains fresh for 300 seconds.

HTTP caching is covered in detail in `09-caching.md`.

# 🗁 HTTP Redirects

An HTTP redirect instructs a client to access a different resource location.

Redirects use status codes in the 3xx category, commonly together with the `Location` header.

### 🖆 Permanent Redirect

`301 Moved Permanently` indicates that the resource has moved permanently.

Example:

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-url
```

### 🖆 Temporary Redirect

`302 Found` indicates a temporary redirect.

Example:

```http
HTTP/1.1 302 Found
Location: https://example.com/temporary-page
```

### 🖆 See Other

`303 See Other` instructs the client to retrieve another resource, commonly using GET.

It is often used after processing a form submission.

### 🖆 Method-Preserving Redirects

`307 Temporary Redirect` and `308 Permanent Redirect` preserve the request method when the client follows the redirect.

This is particularly important for requests such as POST and PUT.

### 🖆 Redirect Comparison

| Status Code | Redirect Type | Method Preservation |
| --- | --- | --- |
| `301` | Permanent | Clients may change POST to GET |
| `302` | Temporary | Clients may change POST to GET |
| `303` | See Other | Follow-up retrieval uses GET or HEAD |
| `307` | Temporary | Preserves method |
| `308` | Permanent | Preserves method |

# 🗁 Response Processing in JavaScript

The Fetch API provides the `Response` interface for handling HTTP responses.

A response object exposes useful properties and methods.

### 🖆 Response Properties

| Property | Description |
| --- | --- |
| `response.status` | HTTP status code |
| `response.statusText` | Reason phrase when available |
| `response.ok` | Whether status is in the 200–299 range |
| `response.headers` | Response headers |
| `response.url` | Final response URL |
| `response.redirected` | Whether the request followed a redirect |
| `response.type` | Response type |

### 🖆 Read JSON Response

```javascript
async function getUsers() {
    const response = await fetch(
        "https://example.com/api/users"
    );

    const users = await response.json();

    console.log(users);
}
```

### 🖆 Read Text Response

```javascript
async function getMessage() {
    const response = await fetch(
        "https://example.com/message"
    );

    const message = await response.text();

    console.log(message);
}
```

### 🖆 Read Blob Response

Blob responses are useful for handling files and binary data.

```javascript
async function downloadImage() {
    const response = await fetch(
        "https://example.com/image.png"
    );

    const imageBlob = await response.blob();

    const imageUrl = URL.createObjectURL(imageBlob);

    const image = document.createElement("img");

    image.src = imageUrl;

    document.body.appendChild(image);
}
```

### 🖆 Inspect Response Headers

```javascript
async function inspectResponse() {
    const response = await fetch(
        "https://example.com/api/users"
    );

    console.log(response.status);
    console.log(response.ok);

    console.log(
        response.headers.get("Content-Type")
    );

    console.log(
        response.headers.get("Cache-Control")
    );
}
```

### 🖆 Handle HTTP Errors

Fetch does not automatically reject its promise for HTTP error statuses such as `404` and `500`.

Check the response status explicitly.

```javascript
async function getUser() {
    try {
        const response = await fetch(
            "https://example.com/api/users/10"
        );

        if (!response.ok) {
            throw new Error(
                `HTTP Error: ${response.status}`
            );
        }

        const user = await response.json();

        console.log(user);
    } catch (error) {
        console.error(error);
    }
}

getUser();
```

### 🖆 Handle Different Status Codes

```javascript
async function createUser() {
    const response = await fetch(
        "https://example.com/api/users",
        {
            method: "POST",
            headers: {
                "Content-Type": "application/json"
            },
            body: JSON.stringify({
                name: "Alice"
            })
        }
    );

    if (response.status === 201) {
        console.log("User created successfully");
        return response.json();
    }

    if (response.status === 400) {
        console.log("Invalid request data");
        return;
    }

    if (response.status === 401) {
        console.log("Authentication required");
        return;
    }

    if (response.status >= 500) {
        console.log("Server error");
        return;
    }

    console.log("Unexpected status:", response.status);
}
```

### 🖆 Handle a 204 Response

A `204 No Content` response has no body. Do not attempt to parse it as JSON.

```javascript
async function deleteUser(id) {
    const response = await fetch(
        `https://example.com/api/users/${id}`,
        {
            method: "DELETE"
        }
    );

    if (!response.ok) {
        throw new Error(
            `Delete failed: ${response.status}`
        );
    }

    if (response.status === 204) {
        console.log("User deleted successfully");
        return;
    }

    return response.json();
}
```

# 🗁 Common Response Errors

### 🖆 Incorrect Content-Type

A server returns JSON but specifies an incorrect media type.

Problematic response:

```http
HTTP/1.1 200 OK
Content-Type: text/plain

{"name":"Alice"}
```

Better response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"name":"Alice"}
```

### 🖆 Returning 200 for Every Operation

Using `200 OK` for every possible outcome makes API behavior difficult to interpret.

Use meaningful status codes:

* `200 OK` for successful requests with a response.
* `201 Created` for successful resource creation.
* `204 No Content` for successful operations without response content.
* `400 Bad Request` for invalid requests.
* `404 Not Found` when the requested resource does not exist.
* `500 Internal Server Error` for unexpected server failures.

### 🖆 Returning a Body with 204

A `204 No Content` response must not contain response content.

Problematic response:

```http
HTTP/1.1 204 No Content
Content-Type: application/json

{"message":"Deleted"}
```

Correct response:

```http
HTTP/1.1 204 No Content
```

If the application needs to return a confirmation message, use an appropriate response such as `200 OK`.

### 🖆 Exposing Internal Server Errors

Returning stack traces, database credentials, SQL statements, or internal infrastructure details can expose sensitive implementation information.

Return a safe error representation and log diagnostic details on the server.

### 🖆 Missing Cache-Control Configuration

Incorrect caching behavior can cause stale or sensitive data to be reused unexpectedly.

Configure caching according to the resource's sensitivity and update frequency.

### 🖆 Incorrect Redirect Status

Using `301` or `302` for an operation that must preserve its request method can produce unexpected behavior.

Use `307` or `308` when method preservation is required.

# 🗁 Best Practices

* Return meaningful HTTP status codes.
* Set the correct `Content-Type` header.
* Use consistent response formats across API endpoints.
* Avoid returning unnecessary response data.
* Do not expose sensitive server information.
* Include useful error messages without revealing implementation details.
* Use `201 Created` when a resource is successfully created.
* Use `204 No Content` when a successful operation has no response content.
* Configure caching intentionally.
* Use `Location` when identifying a newly created resource or redirect destination.
* Apply security headers where appropriate.
* Handle redirects correctly.
* Make frontend applications check `response.ok` or `response.status`.
* Do not attempt to parse empty responses as JSON.
* Document response schemas and status codes for API consumers.

# 🗁 Interview Questions

### 🖆 Fundamental Questions

**What is an HTTP response?**

An HTTP response is a message sent by a server to a client after processing an HTTP request.

**What are the main components of an HTTP/1.1 response?**

A status line, response headers, an empty line, and an optional response body.

**What is a status line?**

It is the first line of an HTTP/1.1 response and contains the HTTP version, status code, and reason phrase.

**What is an HTTP status code?**

A three-digit code that communicates the result of processing an HTTP request.

**What are response headers?**

They provide metadata about the returned response, such as content type, caching instructions, and cookies.

### 🖆 Status Code Questions

**What is the difference between 200 and 201?**

`200 OK` indicates successful processing. `201 Created` indicates that a resource was successfully created.

**What is the difference between 401 and 403?**

`401` indicates missing or invalid authentication credentials. `403` indicates that the server refuses the request, commonly because permission is insufficient.

**What is the difference between 301 and 302?**

`301` indicates a permanent redirect, while `302` indicates a temporary redirect.

**What is the purpose of 204 No Content?**

It indicates that the request succeeded and there is no response content.

**What is the purpose of 304 Not Modified?**

It indicates that a cached representation can be reused without transferring the representation again.

### 🖆 Header Questions

**What is the Content-Type header?**

It identifies the media type of the response body.

**What is the Content-Length header?**

It indicates the length of the message content in octets when applicable.

**What is the Location header?**

It identifies a resource location, commonly used for redirects and newly created resources.

**What is the Set-Cookie header?**

It instructs the client to store a cookie.

**What is the Cache-Control header?**

It defines caching directives for browsers and intermediary caches.

### 🖆 JavaScript Questions

**What is the Response object in Fetch API?**

It represents the response to a Fetch request and provides access to status information, headers, and response-body methods.

**What does response.ok return?**

It returns `true` when the status code is between 200 and 299.

**Does Fetch throw an error for HTTP 404?**

No. Fetch normally resolves with a Response object. Developers must check the status or `response.ok`.

**How do you read a JSON response?**

Use `response.json()`.

**Why should you not call response.json() on a 204 response?**

A 204 response contains no response body, so JSON parsing will fail.
